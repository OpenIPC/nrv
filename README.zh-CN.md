# OpenIPC NVR — 带 AI 侦测与门禁的安防视频服务器

**其他语言版本：**
[Русский](README.md) · [English](README.en.md) · [한국어](README.ko.md)

面向分布式 IP 摄像头（OpenIPC、海康威视、大华、Vivotek、ONVIF）的安防视频服务器，
具备基于神经网络的人物与声音侦测、人脸与车牌识别、门禁系统集成以及网页界面。

```
                        └──────────┘ └─────────┘ │大华/      │
                                                  │Promwad    │
                                                  └───────────┘
```

## 界面语言

界面可在四种语言之间切换：**俄语、英语、中文（简体）和韩语**。默认语言为俄语。

| 语言 | «服务器» 页面上的按钮 | 翻译状态 |
|---|---|---|
| Русский | 默认 | 源语言，完整 |
| English | `English` | 部分完成 |
| 简体中文 | `简体中文` | 部分完成 |
| 한국어（朝鲜） | `한국어` | 部分完成，**用韩国规范**——见下文 |

### 如果语言没有自动切换

第一次打开时，界面会读取浏览器设置中的语言：如果浏览器报告中文或韩语，界面会立即
以该语言打开。但也可能相反——浏览器设为俄语，而使用者需要别的语言；或者浏览器报告
的语言界面不支持，于是显示俄语。这时就需要手动切换语言。

![语言切换器](docs/screenshots/30-language-switch.png)

1. 打开 **服务器** 页面 —— `http://<服务器地址>:3001/server`，就是您平时打开界面
   用的那个地址。
2. 在 **界面语言** 区块中点击所需语言的按钮。该区块位于页面最上方，紧跟在说明文字
   之后：读不懂俄语的人，如果连这里写的是什么都不知道，就根本走不到后面的设置。
3. 所选语言会被打上勾并立即生效——菜单、按钮以及所有页面上的标签都会跟着改变。

选择会保存在浏览器中，所以只需设置一次。它保存在浏览器而不是服务器上：一台工作站
可以是俄语，另一台可以是韩语，彼此互不影响。

同一页面的其他截图：[英文](docs/screenshots/27-language-en.png)、
[中文](docs/screenshots/28-language-zh.png)、
[韩语](docs/screenshots/29-language-ko.png)、

### 为什么国旗是画在代码里的

国旗是以矢量图形直接画在代码里的，既不是 emoji，也不是加载的图片。原因和词典一样：
服务器安装在住宅或办公室里，那里可能完全没有互联网，而在这种网络里任何外部加载都
会变成一片空白。字体上已经吃过这个亏——没有含中日韩字形的字体时，所有中文都显示成
空白的方框。

### 关于韩语

按钮上是**朝鲜**国旗，而文字用的是**韩国规范**。这个不一致是刻意的：本服务器的客户
来自朝鲜，国旗理应是他们国家的。但朝鲜规范并不是「同一个韩语换面旗」，而是一门独立
的翻译语言，有自己的词汇、称谓和术语，必须由母语者来做。靠替换词典里的词是做不到的。

如何参与翻译、如何修正其他语言、如何新增一门语言 ——
[docs/TRANSLATIONS.md](docs/TRANSLATIONS.md)。

## 功能

| 模块 | 已实现的内容 |
|---|---|
| **摄像头** | 通过网页界面添加和编辑（数据存在 PostgreSQL，无需手写配置）、子网扫描器（ONVIF、mDNS、HTTP 探测、账号密码尝试）、**保存前检查视频流**并显示编码、分辨率和是否有声音 |
| **视频流** | 通过 MediaMTX 接收 RTSP、面向浏览器的 HLS、WebRTC、主码流与子码流、经后端代理并带 JWT 鉴权 |
| **对外 RTSP 访问** | 向第三方系统（电视墙、录像机、分析平台）提供视频流，地址为 `/cameras/{N}/streaming/{main\|sub}`，使用独立端口 9784。通道号自动分配，**对外访问**页面提供现成链接。视频流不做转码——摄像头的负载不会增加 |
| **摄像头声音** | 在播放器中收听，自动把 G.711 转为 AAC（浏览器无法在 HLS 中播放 G.711），独立音轨与画面同步 |
| **目标侦测** | 带跟踪的 YOLOv8。精度过滤：置信度阈值、目标最小与最大尺寸、框的宽高比、静止目标过滤。可按摄像头单独设置 —— [docs/DETECTION-QUALITY.md](docs/DETECTION-QUALITY.md) |
| **人脸识别** | InsightFace（ArcFace）：特征向量、已知人脸库，标记为「已知」/「未知」/「禁止」 |
| **车牌识别** | 车牌区域检测、OCR、可配置的搜索区域（避免把摄像头的 OSD 菜单也识别进去）、按地区校验号牌格式 |
| **云台 PTZ** | 通过 ONVIF 控制球机：方向、变焦、停止、预置位、步长调节 |
| **摄像头控制** | 通过固件 HTTP API（Majestic）配置摄像头，无需 SSH：视频、图像、夜视模式、OSD、重启。没有 API 的摄像头仍使用 SSH |
| **其他品牌摄像头** | 直接从摄像头读取设备信息（型号、固件、序列号、MAC）、运行状态（运行时长、CPU 与内存占用、**时钟偏差**）、视频流参数以及**重启**——支持海康威视（ISAPI）、Beward（厂商 HTTP API），以及通用 ONVIF 层：Vivotek、大华、Axis、宇视、Reolink、雄迈。无需 SSH —— [docs/CAMERA-VENDORS.md](docs/CAMERA-VENDORS.md) |
| **摄像头健康度** | 每分钟轮询 `/metrics` 和 `/api/v1/sources`：CPU 占用、可用内存、传感器帧率、编码器丢帧。给出「正常 / 注意 / 问题」的结论并说明原因 |
| **预览图** | 摄像头列表中用一帧画面代替视频流：一次 HTTP 请求替代一个 RTSP 会话。支持 Basic 与 Digest 鉴权，并可从 RTSP 兜底取帧 |
| **事件** | 保存 AI 侦测结果（类别、置信度、边框、轨迹），关联触发条件（目标 / 越线 / 人脸 / 车牌），支持过滤与分页 |
| **录像** | 按触发或持续录像，元数据存入 PostgreSQL，文件存本地或 MinIO，可在浏览器中回放，按保存期限自动清理 |
| **门禁** | 适配海康威视（ISAPI）、大华、Promwad、**IronLogic Z-5R WEB BT**：门列表、开门、通行事件 |
| **权限：人员与权限** | 持卡人（姓名、职务、照片、部门）、权限组、门、权限计算并标明来源。卡类型：普通卡、管理卡、封锁卡。独立的「权限」页面 —— [docs/SKUD-ACCESS.md](docs/SKUD-ACCESS.md) |
| **录入卡片** | 控制器上的 Accept 模式（门对所有人打开，卡片写入内存）以及**从门上读卡器读卡**——卡号进入界面而不必对所有人开门。操作台上的桌面 USB 读卡器相当于键盘 |
| **平面图** | 带设备布置的楼层图：底图上放置摄像头、门、控制器、读卡器（底图可为照片或图纸扫描件）。每个点都能看出设备是否在正常工作 —— [docs/PLANS.md](docs/PLANS.md) |
| **PoE 交换机** | 管理型 PoE 交换机的登记：网络中发现、端口状态（链路、速率、功耗瓦数）、**用断电重启卡死的摄像头**而不必爬上去。保护上行端口不被误关。摄像头与端口的绑定 —— [docs/SWITCHES.md](docs/SWITCHES.md) |
| **服务器设置** | 统一页面：录像与截图的存储路径、本地磁盘或 S3、识别参数 |
| **监控** | 自动判断摄像头状态（在线/离线）、媒体服务器重启后恢复视频流路径、清理「悬空」路径 |
| **通知** | Telegram 与 MAX：带截图或短视频的侦测事件、选择摄像头与事件类型、置信度阈值、免打扰时段、发送日志。另有对服务器本身的监视：摄像头掉线、CPU 占用、内存、磁盘、过热和显卡 |
| **截图** | 按厂商路径取摄像头画面、从 HLS 兜底取帧、事件列表中的截图 |
| **移动应用** | 手机 Android：选择服务器、查看摄像头与录像。另有面向 **Android TV** 的构建：1 至 25 路宫格、布局、声音。详见[下文](#移动应用) |

## 界面

### 摄像头与查看

磁贴显示每台摄像头的实时画面、状态和视频流地址。可直接在磁贴中切换 `main`/`sub`，
并有单独的删除按钮。

![摄像头](docs/screenshots/03-cameras.png)

摄像头卡片中有播放器（主码流或子码流）、声音按钮，球机还有云台控制面板。

![摄像头卡片](docs/screenshots/04-camera-live.png)

播放器旁是设备信息：设备档案（型号、固件、序列号、MAC）、运行状态（运行时长、
CPU 与内存占用、时钟偏差）、视频流参数以及重启按钮。数据是从摄像头本身读的，
而不是取自我们的数据库。

![设备信息](docs/screenshots/21-camera-device.png)

### 声音

摄像头以 G.711 输出声音，浏览器无法在 HLS 中播放，因此系统把它转成 AAC 并以独立
音轨推送。面板上能看到摄像头的编码格式、是否正在转码、以及声音事件是否被识别。

![声音设置](docs/screenshots/05-camera-audio.png)

YAMNet 声音事件：枪声、尖叫、玻璃破碎、狗吠等。可按类别过滤，并高亮告警事件。

![声音事件](docs/screenshots/08-audio-events.png)

### 目标侦测

目标类别、最低置信度、搜索区域和越线。设置作用于指定摄像头，并由侦测器自动加载，
无需重启。

![侦测设置](docs/screenshots/06-camera-detection.png)

侦测到的目标会连同截图、类别、置信度和所属摄像头一起记入日志。

![侦测事件](docs/screenshots/07-events.png)

### 录像

录像记录标明原因（目标、人脸、车牌、越线、连续录像）、大小、分辨率和保存期限。
可直接在浏览器中回放。

![录像](docs/screenshots/09-recordings.png)

### 识别与门禁

已知人脸库和车牌库，状态分为「已知」、「未知」、「禁止」。

![识别](docs/screenshots/10-recognition.png)

扫描器可发现子网中的摄像头，添加前还能检查视频流：编码、分辨率以及是否有声音。

![扫描器](docs/screenshots/12-scanner.png)

### 权限：人员、组与卡

持卡人卡片中的权限是**计算结果**，而不是存储的记录：每一扇门都能看出权限从何而来——
来自权限组还是来自个人规则。否则在处理「他刷不开门」时，就不知道要改哪里。

卡有三种类型：普通通行卡、管理卡（用于编程控制器，不开门）和封锁卡（用于切换模式）。

卡号有两种录入方式：

* **桌面 USB 读卡器**——相当于键盘，卡号直接输入表单字段；
* **门上的读卡器**——操作员点击「等待卡片」，把卡靠近门，卡号就出现在界面上。
  此时门**不会**对所有人打开：服务器只是监听控制器发出的事件。

更多细节，包括厂商文档与实机不符之处 —— [docs/SKUD-ACCESS.md](docs/SKUD-ACCESS.md)。

### 平面图

带设备布置的楼层图：能看出什么东西放在哪里，以及哪一个失联了。

这是独立页面而不是设备列表里的一个标签：列表和平面图回答的是不同的问题。列表回答
「有哪些摄像头」，平面图回答「这个通道口上装着什么」。巡视和排查事故时，需要的正是
后者。

![平面图](docs/screenshots/18-plans.png)

在底图（楼层照片或图纸扫描件）上放置摄像头、门、控制器和读卡器。设备正常时图标为
绿色，失联时为红色，设备已删除或只是没有绑定设备的位置标记则为灰色。图标形状区分
设备种类。

坐标以底图尺寸的比例保存，因此可以把底图换成另一尺寸的图片——布局不会错位。状态
每分钟刷新一次，平面图顶部会显示有多少设备不在线。详见 [docs/PLANS.md](docs/PLANS.md)。

### PoE 交换机

管理型 PoE 交换机的登记与摄像头供电控制。

这个页面回答了摄像头列表悬而未决的问题：设备为什么不见了。「离线」并没有说明原因，
而原因有三种——摄像头卡死、线路中断、供电被切断——操作员在每种情况下要做的事都不一样。

![交换机](docs/screenshots/19-switches.png)

交换机通过广播发现，一键即可添加。卡片上显示端口表格：链路与速率、PoE 状态、功耗
瓦数、绑定的摄像头。每个端口都可以开启、关闭或断电重启——后者正是爬上去重启卡死
摄像头的替代方案。

卡死的摄像头可以直接在卡片中重启：**连接**区块会综合端口供电、链路状态和摄像头
自身状态，给出结论，而不是把两个数字摆在一起让操作员自己猜。

![摄像头连接](docs/screenshots/20-camera-network.png)

上行端口受到保护，不允许关闭：与服务器之间的链路经过它们，一旦断电，整台交换机都
可能失控。每次操作都会记入日志，标明是谁在什么时候执行的。更多细节，包括不同型号
之间的差异 —— [docs/SWITCHES.md](docs/SWITCHES.md)。

### 设置与总览

统一的设置页面：录像与截图的存放位置（磁盘或 S3）、识别参数、保存期限。

![设置](docs/screenshots/11-settings.png)

系统状态总览：在线摄像头数、24 小时事件数、已占用空间。

![仪表盘](docs/screenshots/02-dashboard.png)

### 通知

事件会发送到 Telegram 和 MAX：截图或短视频、选择摄像头、事件类型、置信度阈值和
免打扰时段。每个通道单独配置，一个失败不影响另一个。

![Telegram 通知](docs/screenshots/14-notify-telegram.png)

MAX 是唯一能从俄罗斯直接访问、无需代理的通道。它的 REST API 对消息格式要求明显
更严，因此文本是单独拼装的，而不是复用 Telegram 的。

![MAX 通知](docs/screenshots/15-notify-max.png)

另有一个标签页用于监视服务器本身：摄像头掉线、CPU 占用过高、内存不足、磁盘将满、
过热、显卡故障。测量温度和显卡需要在宿主机上安装代理：从容器里看不到这些。

![服务器通知](docs/screenshots/16-notify-system.png)

日志显示什么发到了哪里、以及为什么有些没发出去——例如某个事件类型没有勾选发送。
不必打开即时通讯软件，就能看出投递状态。

![通知日志](docs/screenshots/17-notify-log.png)

> 截图取自真实系统。在服务器运行时可用 `node scripts/make-screenshots.js` 重新生成。
> 截图中的令牌和聊天地址会自动抹去。

## 移动应用

同一个 React Native 应用会构建成两种形态：手机版和电视版。形态按设备类型自动选择——
在电视上手机界面虽然能用，但用遥控器根本点不中。

### 手机

按 IP 地址、端口或 DNS 名称连接服务器，实时查看摄像头并使用录像。

| 界面 | 功能 |
|---|---|
| **服务器** | 已保存服务器列表、添加、保存前检查连通性、切换、删除 |
| **登录** | 用户名与密码；令牌按服务器分别保存，因此切换服务器无需重新登录 |
| **摄像头** | 带预览画面的磁贴（每 10 秒刷新）、在线/离线状态、下拉刷新 |
| **查看** | 通过 HLS 播放实时视频、切换主码流与子码流、暂停、声音 |
| **录像** | 支持按摄像头过滤的录像列表、带进度拖动的内置播放器、滚动加载。录像原因一眼可见：车牌、人脸、目标 |

| 服务器 | 摄像头 | 录像：车牌 | 录像：目标 |
|---|---|---|---|
| ![](docs/screenshots/mobile/01-servers.jpg) | ![](docs/screenshots/mobile/02-cameras.jpg) | ![](docs/screenshots/mobile/04-archive-plates.jpg) | ![](docs/screenshots/mobile/05-archive-objects.jpg) |

服务器名称旁的计数器显示在线摄像头数占总数的比例：截图中为 22 台中的 19 台。摄像头
可按地址过滤，录像可直接从列表中打开——例如「未知：P263AT54」。

### Android TV

面向电视和机顶盒的构建：最多 25 路宫格、布局和声音。用遥控器操作，磁贴够大——
坐在沙发上也能看清。

![电视上的 4×4 宫格](docs/screenshots/tv/01-grid-4x4.jpg)

**宫格：** 1、2、4、6、9、16 和 25 路。形状按电视屏幕来选择，而不是做成正方形：
6 路是 3×2 而不是 2×3，否则磁贴会被拉长，两侧留下黑边。

**布局：** 摄像头组合、宫格尺寸、标签和声音可存为具名布局（「入口」、「夜班」），
一键切换。每台服务器有各自的布局。所选摄像头的顺序决定它们在宫格中的位置，因此选择
列表显示的是磁贴编号而不是勾选框。

**声音：** 一次只开启一台摄像头的声音。多路摄像头同时出声会混成噪音，而操作员需要
的是某一台。

> 在密集宫格（16 和 25 路）中，磁贴上的标签会自动隐藏：这种磁贴只有约一百像素，
> 名字会遮住一半画面。只保留角落里的状态点。

声音走独立音轨：MediaMTX 推送的视频不带声音，服务器单独发布音频流。宫格中播放的是
子码流而不是主码流——四路 4K 主码流需要超过 60 Mbit/s，电视的 Wi-Fi 和它的解码器
都吃不消。

| 界面 | 功能 |
|---|---|
| **宫格** | 按布局显示摄像头、磁贴获得焦点、按「OK」全屏打开或开启声音 |
| **布局** | 新建、选择、删除；每个布局有宫格尺寸和摄像头组合 |
| **摄像头** | 为布局选择摄像头，顺序决定位置 |
| **设置** | 标签（名称、状态、时钟）、声音、音量、开启声音的摄像头 |

## 已知限制

| 限制 | 原因 | 应对办法 |
|---|---|---|
| 通过摄像头喇叭的双向对讲不可用 | 摄像头不支持反向音频通道：`RTSP OPTIONS` 的响应中没有 `ANNOUNCE` 和 `RECORD` 方法。管线已实现，在支持该功能的摄像头上即可工作 | 会自动检测：只有在支持时才显示对讲按钮 |
| 声音侦测占用 CPU | YAMNet 跑在 CPU 上，以免与目标侦测争夺 GPU | 在摄像头设置中关闭不需要的摄像头或声音类别 |
| WireGuard 隧道不能自动管理 | `internal/tunnel/wg_manager.go` 只是雏形，没有与 netlink 集成 | 用 `wg-quick` 手动配置对端 |
| 温度和显卡状态只能通过代理查看 | 从容器内无法访问宿主机的传感器和 GPU | 在宿主机上安装 `host-agent`：`sudo install -m 0755 agent.py /opt/nvr-agent/agent.py` |
| 韩语界面用的是韩国规范，而旗子是朝鲜的 | 朝鲜规范是一门独立语言（`ko-KP`），有自己的规则和术语，需要母语者。而旗子理应是客户所在国家的 | 临时措施。需要一位熟悉朝鲜规范的校对者：[docs/TRANSLATIONS.md](docs/TRANSLATIONS.md) |
| 部分错误提示仍为俄语 | 它们由后端根据设备的应答拼出来，而不是界面，也不属于文案 | 随着迁移推进而减少。位置清单见：[docs/TRANSLATIONS.md](docs/TRANSLATIONS.md) |
| 中文和韩语需要含中日韩字形的字体 | 矢量图形总是能画出来，但汉字是文本，由系统字体渲染 | 在打开界面的机器上安装 Noto Sans SC / Noto Sans KR |

## 更新日志

### 2026-10-04 — 界面语言：俄语、英语、中文、韩语

**界面可在四种语言之间切换。** 切换器位于服务器设置页面，与时间和网络设置放在一起。
选择会保存在浏览器中，因此不同工作站的界面语言可以不同——服务器不保存任何相关数据。

**语言以国旗表示，而图片是代码里的矢量图形。** 没有任何外部加载：服务器所在网络可能
完全没有互联网，而旗子位置出现空白，我们已经吃过这个亏——就像中日韩字体那样。

**界面文案已全部翻译。** 每个页面都用中文和韩文走查过：只剩摄像机和控制器的名
称是俄语——那是人工填写的。俄语仍作为兜底语言，万一漏掉一条，用户看到的是文字
而不是 `nav.cameras` 这样的键名。

**韩语的情况如实说明。** 文字用的是**韩国规范**，而切换器上是**朝鲜**国旗——这是应
当地客户的要求。朝鲜规范是一门独立的语言，有自己的词汇和术语，需要母语者。目前旗子
和规范并不一致，这一点写在 [docs/TRANSLATIONS.md](docs/TRANSLATIONS.md) 中，那里
也有如何修正翻译和新增语言的说明。

### 2026-10-03 — 门禁接入 Beward 对讲机：开门并记录

**对讲机作为门禁设备接入了门禁系统。** DS07P-LP 有锁控继电器和呼叫按钮，而门禁模块
里已经有通行日志、事件抓拍和录像——所以对讲机放在那里说明，而不是和摄像头放在一起。

**现场是怎么接的。** 对讲机的继电器接到 Z5R 控制器的「出门按钮」输入端。

**这对日志意味着什么——而这正是采用这种接法的根本原因。** 对 Z5R 来说，从对讲机
开门看起来就像是按了出门按钮，而不是刷卡通行。门禁事件中本来就有这类记录：
`event_type=exit_button`。从这些记录**无法判断是谁开的门、从哪里开的**——是从对讲机、
从 Z5R 的网页界面，还是门口真正的按钮。这三种情况完全无法区分。所以我们自己做日志：
只有这样才会留下「门是对讲机打开的」这条痕迹。

**一次开门会产生两条记录**——我们自己的（带原因）和 Z5R 发来的 `exit_button`。这不是
两次通行，而是同一个动作从两侧被看到。

**门的状态显示为「未知」，这是诚实的做法。** 设备只上报告警，在我们验证过的那台上
永远返回 `NO Alarm`。门的位置读不出来。在不知情的情况下显示「已锁」，和当初摄像头
时钟读不出来却显示「准确」是同一个错误。

**在实机上验证过的内容：** 连通性（控制器 `online`）和门列表。**开门操作没有验证**
——验证就意味着要真去开一扇门。地址和命令参数是按接口说明核对的，并在模拟设备上有
测试覆盖。

**SIP 和声音在现场已经配好**，我们暂时没有使用：注册到 SIP 服务器、呼叫两个号码、
通话中按数字键会闭合继电器。设备侧的双向声音已开启（`DoubleAudio=on`）——麦克风和
喇叭会送进我们本来就在接收的 RTSP 流。

详见 [docs/SKUD-ACCESS.md](docs/SKUD-ACCESS.md)。

### 2026-10-03 — Beward 摄像头：厂商 HTTP API

**厂商提供了完整的接口说明**——219 页、63 个不同的地址。它覆盖了设备的全部配置，
比 ONVIF 给出的多一个数量级。

**Beward 以厂商 API 为主，ONVIF 作为备用。** ONVIF 在这些设备上能用，但根本不报告
运行时长。厂商 API 会报告，现在卡片上能看到设备上次启动的时间。此外，如果设备上关掉
了 ONVIF，厂商接口依然可用。

**鉴权用 Digest，并保留 Basic 作为后备。** 说明中两种都允许；没有后备的话，配置成
Basic 的设备就会变得无法访问。

**发现两个错误，第二个比第一个更危险。** 设备时间被当作世界时解析并换算成本地时
间——读数整整差了时区偏移量，对讲机时钟显示 `17:24` 而不是 `14:24`。时间必须在本地
时区重新组装，而不是把一个时刻做换算。

第二个是在截图上暴露的：当读不到时钟时，卡片显示「01.01.1」——一个凭空编造的日期，
并把偏差输出为**「准确」**。也就是说，缺失的数据变成了「摄像头时钟正常」的断言，
操作员也就不会去检查一个已经被确认正常的东西。现在缺失的数据就表现为缺失——那一行
直接不显示，和 ONVIF 的码率一样。

**两个来源互相印证。** 响应里没有单独的序列号字段，但 `DeviceID` 就是序列号：同一台
设备通过 ONVIF 报告的正是这个值（`293239`）。这是验证，不是猜测。

**这个型号没有人脸识别。** 说明里有这一节，但 `facecfg_cgi` 返回 `404`：功能集合
取决于型号，而不是说明的版本。

**顺带弄清了为什么 ONVIF 在 Beward 上能用、在海康威视上不能。** Beward 出厂就开启
了 ONVIF（`root.Properties.API.ONVIF.ONVIF=yes`），而海康的摄像头上从来没开过，
也没创建过 ONVIF 用户。

详见 [docs/CAMERA-VENDORS.md](docs/CAMERA-VENDORS.md)。

### 2026-10-03 — 其他厂商摄像头：通用 ONVIF 层与海康威视

**直接从摄像头读取设备信息与状态。** 摄像头卡片上新增了**设备**区块：型号、固件、
序列号、MAC、运行时长、CPU 与内存占用、视频流参数。数据从摄像头本身读取，而不是取自
我们的数据库——与已记录内容不符本身就是需要关注的理由。

**无需 SSH 即可重启。** 设备卡片上带确认的按钮。在实机上验证过：80 秒（海康威视）
和 60 秒（Vivotek）后恢复。

**两级访问方式。** 通用 ONVIF——一套代码支持所有品牌；在通用语言能提供的东西更少的
地方，用海康威视的厂商适配器（ISAPI）补充。

**为什么海康威视不走 ONVIF。** 现场摄像头上 ONVIF 失败了：预备性调用能通过，但需要
鉴权的调用被拒绝并返回「sender is not authorized」。原因不在代码——摄像头上没有开启
ONVIF，也没有创建 ONVIF 用户，网页用户不算。用同样的密码走 HTTP Digest 则立刻可用。

**时钟偏差在界面中可见。** 摄像头 `192.168.1.63` 的时钟慢了 **139 天**——这在卡片上
直接就能看到。以前只能通过录像里错位的时标间接发现。

**发现并修复了三个错误：**

* 时钟偏差的正负号弄反了：正值表示慢，却显示成「快」。在一台慢 139 天的摄像头上
  验证过。
* 在必然会被拒绝的地方也显示了重启按钮：能力检查放在了类型断言之后，而在适配器
  链上这个断言永远成立。
* 媒体服务地址是原样从摄像头取的。对于隧道后面的摄像头，那里记的是它自己的内网地址
  ——在设备完全正常的情况下，请求也发到了空处。现在只替换主机，端口和路径保持不变。

**鉴权被抽到公共包** `internal/httpdigest`——并在重试前恢复请求体。重启海康威视需要
非空的请求体，如果不恢复，命令就会悄无声息地失效。

详见 [docs/CAMERA-VENDORS.md](docs/CAMERA-VENDORS.md)。

### 2026-10-02 — 通过 MAC 表自动判断摄像头绑定关系

**摄像头与端口的绑定关系可自动判断**

交换机会维护 MAC 地址表，并报告每个地址从哪个端口可见。系统把这些地址与摄像头
数据库比对，自己给出绑定建议——端口不再需要手动填写。

- 交换机页面显示端口上的所有设备，包括不属于摄像头的那些：这有助于发现多余设备
- 「自动识别摄像头绑定」按钮会找出匹配项并显示将会发生什么变化
- 上行端口后面的设备单独标注：它们并不接在这台交换机上，绑定到这里是错误的

筛选规则刻意收得很窄，因为出错的代价很高——错误绑定会导致给错误的摄像头断电重启。
只有当地址在恰好一个 PoE 端口上可见、并且恰好对应本项目的一台摄像头时，才会给出建议。

**不同型号行为不同，这一点在界面上就能看出来**

有三种情况：上报端口（自动绑定）、有表但没有端口（手动绑定）、不支持该命令。在现场
设备上三种都遇到了，而且有一台交换机的固件对所有记录返回相同的掩码，连自身端口上的
设备也一样。

**修正了端口编号**

反转规则取自交换机自带的网页界面，并在两个型号上验证过。此前的版本把整个端口列表
反转，而设备**只反转 PoE 端口**，上行端口留在末尾。在 GPS204V3 上这意味着发给 1 号
端口的命令会落到上行端口——那正是与服务器通信的链路。

规则不是猜的：GPS204V3 的界面上，四个 PoE 端口对应的 `portIndex` 为 `[3,2,1,0]`，
而 PS208GV3 上为 `[0..7]`。

> **升级时注意：** 该修正会改变采用反向顺序的型号上已保存绑定的含义。请检查此前
> 创建的绑定。

**在实机上验证过**

整条链路：系统识别出 1 号端口上的摄像头，对该端口断电重启后关掉的正是它，恢复供电
后摄像头又回到表中同一个端口。

### 2026-10-02 — PoE 交换机管理

**交换机登记与端口监控**

独立页面：在网络中发现交换机、端口状态、操作日志。支持管理型 SSCPOE PoE 交换机——
已在 PS204、PS208GV3 和 GPS204V3 上验证。

- 广播发现：无需事先知道地址，用序列号作为标识
- 端口表格：链路与速率、PoE 状态、**功耗瓦数**、收发流量、绑定的摄像头
- 后台每分钟轮询一次，不开着界面也能拿到状态

**用断电重启卡死的摄像头**

停止响应的摄像头按一下按钮即可重启——不用爬上去。供电循环在实机上验证过：端口断电、
停顿、再送电。

**摄像头与端口的绑定**

摄像头卡片上能看到它接在哪台交换机的哪个端口。区块会综合端口供电、链路存在与否和
摄像头自身状态，给出结论：

- 有供电也有链路，但摄像头不应答——卡死了，重启能解决
- 有供电但没有链路——线路中断，重启没用
- 没有供电——摄像头已断电

**对危险操作的保护**

- 上行端口不允许关闭：与服务器之间的链路经过它们，断电可能导致整台交换机失控
- 不支持 PoE 的端口不接受供电命令
- 绑定到不存在的端口会被拒绝
- 供电操作需要确认

**在实机上发现的不同型号差异**

同一产品线的行为并不一致，这些都已考虑：

- 部分型号无需鉴权就上报状态，部分需要密码；需要登录是一种独立状态，而不是「没有链路」
- 温度放在不同字段里，而且其中一个型号的「温度」字段里是一个不相干的数字
- 端口总数与 PoE 端口数不同：GPS204V3 有六个端口，但只有四个能供电
- 部分型号的端口编号顺序是反的；该标志保存在设置里，可以手动修正，因为这里出错就
  意味着命令发给了错误的端口

**从截图中移除了摄像头密码**

发现界面截图里出现了形如 `rtsp://admin:密码@…` 的视频流地址——也就是把摄像头凭据
以明文形式放进了公开文档。现在截图脚本会对**每一张**图抹掉视频流地址中的
用户名:密码，而不是由截图作者自行决定。

如果您发布过这个项目，请更换摄像头密码：旧版本的截图仍留在 git 历史中。

### 2026-09-26 — 通知、手机与 Android TV 应用

**Telegram 与 MAX 通知**

事件会带着截图或短视频发送到即时通讯软件。在实际使用中验证过：投递、附件、发送日志。

- 侦测事件：目标、车牌、人脸、越线、门禁、声音
- 每个通道可单独选择摄像头和事件类型
- 置信度阈值、重复之间的间隔、免打扰时段
- 在指定时间发送当日汇总
- 发送日志：发了什么、没发什么以及为什么
- 一个通道故障不会阻塞另一个：Telegram 不可用时，MAX 继续工作
- **MAX**——面向俄罗斯的第二通道：可直连，无需代理。它的消息文本是单独拼装的：
  MAX 的 API 对标记更严格，不接受原样的 Telegram 消息

**对服务器与摄像头的监视**

独立标签页回答的是「什么算问题」，而不是「往哪里发」：消息发到同样的通道。

- 摄像头从网络消失——带延时，以免在重启时误报
- 服务器启动时摄像头不可达——立即报告
- 摄像头恢复在线——看得出问题已经过去
- CPU 占用过高、内存不足、磁盘将满
- 设备过热与显卡问题
- 问题解决之前反复提醒，以及免打扰时段
- 温度与显卡由宿主机上的代理测量：从容器里看不到

**通知中的时间**

消息里的时间是 UTC：宿主机的时区没有被传入镜像。现在所有容器都挂载了
`/etc/localtime`，PostgreSQL 另外还拿到 `TZ` 和 `PGTZ`——它的时区取自数据目录，
只挂载一个时区文件对它来说不够。

**手机应用**

- 查看摄像头，带预览画面和在线/离线状态
- 录像并标明原因：车牌、人脸、目标——在列表中就能看到
- 摄像头声音
- 每台服务器一个独立令牌：切换服务器无需重新登录

**Android TV 应用**

- 1 至 25 路宫格，形状按电视屏幕选择
- 具名布局：摄像头组合、宫格尺寸、标签、声音
- 一次只开一台摄像头的声音
- 遥控器操作，元素按观看距离放大
- 在密集宫格中标签会自动隐藏：小磁贴里它们会遮住画面

### 2026-09-22 — 对外 RTSP 访问、无需 SSH 的摄像头控制、按帧预览

**对外 RTSP 访问**

向第三方系统提供视频流：电视墙、录像机、第三方分析平台。外部使用者从 NVR 取流，
不直接连接摄像头——这减轻了对并发 RTSP 会话数有限制的设备的压力。

- 地址 `/cameras/{N}/streaming/{main|sub}`，使用独立端口 `9784`
  （通道号带减一偏移：通道 1 → `cameras/0`）
- 独立鉴权：外部系统只读，内部使用者照旧
- 视频流**不转码**——CPU 负载不增加
- **对外访问**页面：连接参数、可复制的现成链接、通道状态
- 添加摄像头时自动分配通道号
- 详见 [docs/EXTERNAL-RTSP.md](docs/EXTERNAL-RTSP.md)

**无需 SSH 的摄像头控制**

- 通过固件 HTTP API（Majestic）配置摄像头：视频（帧率、码率、编码、分辨率）、
  图像（亮度、对比度、饱和度、镜像）、夜视模式、OSD
- 只发送被修改的字段——摄像头的其他设置不受影响
- 写入前校验取值：摄像头算力有限，错误的码率会把视频流弄挂
- 通过 API 而不是 SSH 重启摄像头
- 支持两套端点集合不同的固件构建
- 没有 API 的摄像头仍使用 SSH

**摄像头健康度**

- 每分钟轮询 `/metrics` 和 `/api/v1/sources`
- 指标：CPU 占用、可用内存、传感器帧率、编码器丢帧、夜视模式
- 给出「正常 / 注意 / 问题」的结论并说明原因
- 指标在摄像头列表和摄像头卡片中都能看到

**用帧预览代替视频流**

- 摄像头列表中用一帧画面代替 HLS 视频流：一次 HTTP 请求替代一个 RTSP 会话，对
  摄像头数量较多的现场明显更省
- 在服务器上缩小画面：4K → 480 点（470 KB → 17 KB）
- 支持 Basic 与 Digest 鉴权、厂商特定的取帧路径
- 没有 HTTP 端点时，从视频流中兜底取帧
- 请求队列：同时最多轮询三台摄像头

**其他**

- 视频流中的 OSD 文字输出已写入文档：标记由摄像头嵌入，录像、浏览器和外部系统看到的
  都是同一个
- 移除了视频流恢复过程中临时的调试日志

### 2026-09-19 — 声音、识别、摄像头控制

**摄像头声音**
- 在播放器中收听声音：独立音轨，与画面同步
- G.711 → AAC 转码：浏览器无法在 HLS 中播放 G.711
- 把声音转发到独立的 MediaMTX 流，视频不受影响

**声音侦测**
- YAMNet（AudioSet 的 521 个类别）：枪声、尖叫、惨叫、玻璃破碎、爆炸、狗吠、警笛、
  汽车报警、说话、音乐
- 可按摄像头设置阈值、类别和冷却时间
- 按音量剔除静音段——防止麦克风底噪造成误报
- 界面中的 **声音** 页面：按类别过滤，告警事件高亮显示

**人脸与车牌识别**
- 已知人脸库和车牌库，标记为「已知」/「未知」/「禁止」
- 可配置的车牌搜索区域——OCR 不再把摄像头的 OSD 菜单识别进去
- 结合地区校验号牌格式

**录像与录制**
- 按触发（目标、越线、人脸、车牌）或持续录像
- 文件名中写明触发原因——能看出录像为什么开始
- 可在浏览器中回放，可选存储位置（本地磁盘或 S3）

**摄像头控制**
- 完整的网页界面控制：数据存在 PostgreSQL，无需手写配置
- 保存前检查视频流：编码、分辨率、是否有声音
- 从 RTSP 地址自动填入 IP
- 修改 IP 和密码时会自动更新媒体服务器路径
- 重启摄像头及其串流器的按钮
- 自动识别没有麦克风和喇叭的摄像头

**GPU 加速**
- 在 CUDA 上侦测（NVIDIA P104-100）：每帧约 13 毫秒，而 CPU 上是 83 毫秒
