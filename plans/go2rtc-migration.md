# Миграция с MediaMTX на go2rtc

**Статус: выполнено 2026-10-05.** MediaMTX и его конфиг удалены, потоки
регистрирует бэкенд, браузер смотрит через go2rtc (MSE и WebRTC). HLS из
браузера убран, но оставлен для нативных клиентов (мобильное приложение)
— см. «Транспорты просмотра».

## Почему перешли на go2rtc

Проект строится как **локальная** система видеонаблюдения: многоквартирные
дома, торговые центры, офисы. Отсюда три требования, которые и определили
выбор медиасервера.

**1. Много камер и большая нагрузка.** В одном объекте — десятки камер, и все
они должны работать одновременно: запись, живой просмотр, детекция, внешние
потребители. Прежний медиасервер держал соединение с каждой камерой постоянно
и занимал под это около 90% процессора ещё до того, как картинку кто-то
открыл. go2rtc подключается к камере **только когда её смотрят**: тот же парк
из 24 камер стал стоить 15–21% вместо 217%, а память — 34 МБ вместо 118.
На объекте с сотней камер эта разница решает, сколько ещё задач потянет сервер.

**2. Всё локально, без облаков.** Ни один кадр не должен уходить на сторону:
это данные о жильцах и посетителях. go2rtc — обычный локальный процесс,
который не требует ни аккаунта, ни интернет-сервиса, ни телеметрии. Он сам
подключается к камерам в локальной сети и сам отдаёт поток браузеру внутри
той же сети. Мы контролируем, что и куда передаётся, и можем показать это
на схеме, а не поверить на слово.

**3. Контроль над тем, что где и как.** Настройки живут в файле рядом с
сервисом, потоки регистрирует наш бэкенд через открытый API, а кадры и звук
можно проверить штатными инструментами (ffprobe, curl). Нет скрытых сущностей
в чужом облаке — есть поток, путь и лог, которые видно и можно измерить.

Плюс к этому go2rtc дал то, чего у прежнего сервера не было вовсе:
**двусторонний звук** из коробки (backchannel по ONVIF Profile T — работает
на камерах OpenIPC), **режим MSE** (задержка как у WebRTC, но по обычному
WebSocket, без UDP), **HTTP-кадры** одним запросом и встроенное
перекодирование звука. Подробности и замеры — ниже.

Переход подтверждён на живом парке: запуск видео ускорился и в браузере, и
во внешних потребителях (в том числе в интеграции Home Assistant, которая
берёт потоки через внешний RTSP-доступ).

## Результат

| | MediaMTX | go2rtc |
|---|---|---|
| CPU (24 камеры) | 217% | **15–21%** |
| Память | 118 МБ | 23–34 МБ |
| Звук | внешний ffmpeg + публикация | встроенный ffmpeg, `#audio=aac` |
| Двусторонний звук | нет | есть (4 камеры OpenIPC) |
| Загрузка сервера | load average 26,9 | **0,8** |

Проверено на живом: 99 потоков зарегистрированы, HLS через прокси бэкенда
отдаёт плейлист (200), внешний RTSP на 9784 отдаёт `h264`, звук — `aac`,
статусы камер обновляются (23 online из 24, одна камера выключена).

Ниже — что именно надо заменить и почему. Всё проверено на живых камерах.

## Что мы используем у MediaMTX

| Задача | MediaMTX | go2rtc |
|---|---|---|
| Регистрация источника | `POST /v3/config/paths/add/<id>` | `PUT /api/streams?name=<id>&src=<url>` |
| Обновление адреса | delete + add (PATCH не работает) | `DELETE /api/streams?src=<id>` + `PUT` |
| Удаление | `DELETE /v3/config/paths/delete/<id>` | `DELETE /api/streams?src=<id>` |
| Список потоков | `GET /v3/config/paths/list` | `GET /api/streams` |
| Приём публикации | путь `source: publisher` | **не нужен** — см. ниже |
| WebRTC браузеру | `POST /<id>/whep` | `POST /api/webrtc?src=<id>` (тоже WHEP) |
| HLS нативным клиентам | `GET /<id>/index.m3u8` | `GET /api/stream.m3u8?src=<id>` (через прокси бэкенда) |
| MSE | нет | `ws://.../api/ws?src=<id>` |

## Проверенные на живом факты (важно для реализации)

1. **Параметры API — в строке запроса.** `PUT /api/streams?name=X&src=Y`.
   Если передать их в теле, приходит `200` и пустой объект, поток не
   создаётся. Это ловушка: ошибка выглядит как успех.
2. **Удаление — по параметру `src`**, не `name`: `DELETE /api/streams?src=X`.
3. **Публикация в неизвестный поток отклоняется** (ffmpeg получает
   «Broken pipe»). Отдельный путь-приёмник для звука создавать не нужно:
4. **Звук отдаёт сам go2rtc.** Поток вида
   `ffmpeg:rtsp://localhost:8554/<id>#audio=aac` заставляет go2rtc запустить
   ffmpeg, перекодировать звук в AAC и отдать его. Проверено: ffprobe
   получает `aac,audio`. Это заменяет наш внешний аудиоконвейер целиком.
5. **Двусторонний звук — это просто второй источник** у того же потока:
   `rtsp://.../<id>#backchannel=1`. go2rtc сам согласует кодеки и отправит
   микрофон браузера в камеру (WebRTC). Работает на 4 камерах из 24 — тех,
   что отдают `a=sendonly` в SDP (`.12`, `.75`, `.87`, `.106`, все OpenIPC).
6. **Ленивость.** go2rtc подключается к камере только когда её смотрят.
   Побочный эффект: `GET /api/streams` НЕ сообщает, жива ли камера
   (в ответе только список адресов). Проверка статуса переезжает с
   медиасервера на `camera_health_service` (проверка самой камеры) —
   это правильнее: медиасервер не средство мониторинга. Ещё один побочный
   эффект: параллельная регистрация потоков и чтение `/api/streams` — гонка
   внутри go2rtc, запрос списка может упасть с паникой
   (`index out of range` в JSON-сериализации); паника глушится обработчиком
   HTTP, сервис живёт. Пример ещё одной причины не строить мониторинг на
   этом запросе.
7. **MSE: codecs — только в открытый WebSocket.** Браузерное API требует
   отдать список кодеков на `sourceopen` у MediaSource, но WebSocket может
   ещё быть в состоянии CONNECTING — тогда `ws.send()` падает с
   `InvalidStateError`, и в сетке камер не играет ни одна плитка. Отправлять
   надо по факту: из `sourceopen` и из `ws.onopen`, проверяя оба состояния.
8. **Пароль RTSP переехал в конфиг go2rtc — и это чуть не потерялось.**
   У MediaMTX учётные данные внешнего доступа жили в `mediamtx.yml`, и при
   переходе их никто не перенёс: порт 9784 какое-то время отвечал любому
   в сети (проверено: `ffprobe` без логина получал `h264`). Нашлось это
   только проверкой доступа руками — по логам и статусам всё выглядело
   исправным.

   Теперь: `rtsp.username` / `rtsp.password` в `go2rtc.yaml`, значения
   берутся из `EXTERNAL_RTSP_USER` / `EXTERNAL_RTSP_PASS`. Ключевая
   особенность go2rtc: **проверка не применяется к localhost** — поэтому
   внутренним потребителям (ffmpeg звука, бэкенд, alias-источники)
   пароль не нужен, а детектору в bridge-сети нужен (ему адрес передаётся
   вместе с данными). Проверено: 9784 без данных → `401`, с данными →
   `h264`, с `127.0.0.1` без данных → `h264`.
9. **HLS отдаётся по API-порту.** Ключ `hls.listen` в 1.9.14 игнорируется:
   порт 8888 не открывается, а плейлист и сегменты отдаёт `:1984`
   (`/api/stream.m3u8`, `/api/stream.ts`). Проверено на живом
   (`index.m3u8` → `playlist.m3u8` → `segment.ts`, все ответы 200).
11. **WHEP отвечает 201 Created, а не 200.** Это стандарт: новая сессия
   создаётся с кодом 201. Прокси в бэкенде, который считал успехом только 200,
   возвращал клиенту 502 при полностью рабочем обмене — ошибка выглядела как
   «медиасервер отказал». Проверять нужно весь диапазон 2xx.
12. **Двусторонний звук требует второго источника, а не публикации.**
   go2rtc не принимает публикацию в неизвестный поток, поэтому прежняя схема
   «ffmpeg публикует звук оператора в путь `<id>_talk`» с ним не работает.
   Правильно — добавить потоку камеры вторым источником адрес с
   `#backchannel=1`: тогда микрофон клиента уходит в камеру тем же WebRTC-соединением.
   Источник ленивый: в `/api/streams` видны оба адреса, но `sdp` только у
   активного, и подключений к камере — ноль, пока никто не заговорил.
13. **Признак обратного канала видно только в ONVIF-запросе.** Камера помечает
   аудиодорожку `a=sendonly` лишь в ответ на DESCRIBE с заголовком
   `Require: www.onvif.org/ver20/backchannel`. Прежняя проверка по ответу на
   OPTIONS давала ложное «нет»: на OPTIONS без учётных данных камеры отвечают
   401 без заголовка Public, и поддержка терялась.
14. **Замер обратного канала по парку (DESCRIBE с `Require: backchannel`).**
   Динамик есть у `.12`, `.34`, `.41`, `.75`, `.87`, `.106` — камеры объявляют
   дорожку `audio-backchannel`. У `.5` и `.61` её нет: там динамика нет вовсе.
   Промежуточный вывод «поддерживает только `.106`» был ошибкой ИЗМЕРЕНИЯ —
   разбор видел лишь первую аудиосекцию (см. пункт 15). Напоминание: сомнительный
   результат проверки сначала перепроверяем на самой камере, а не списываем на
   «прошивка не умеет».

15. **Обратный канал объявлен ВТОРОЙ аудиодорожкой — и это чуть не потерялось.**
   У камер Majestic (`OpenIPC`) в ответ на DESCRIBE приходят ДВЕ аудиосекции:

   ```
   m=audio ... PCMA                                    a=control:audio
   m=audio ... PCMU   a=sendonly   a=control:audio-backchannel
   ```

   Первая — звук с камеры, вторая — обратный канал. Наш детектор разбирал только
   первую секцию, поэтому показывал «нет» на исправных камерах: `.34`, `.75`, `.12`,
   `.87`, `.41`, `.106`. Оператор не видел кнопку «Говорить» там, где звук на камеру
   идёт. Проверено замером на живом: у `.5` и `.61` обратного канала нет вовсе (там
   динамика нет) — то есть признак различает камеры, а не срабатывает у всех.

   Исправлено: признак ищется во ВСЕХ аудиосекциях (`audioSections`), а видео-секцию
   смотреть нельзя — в ней тоже бывает `a=sendonly` (камера отправляет видео).
16. **Запись настроек на `.34` работает не для всех полей и не сразу.**
   `POST /api/v1/config.json` принимает точечный патч и отвечает `200`, но
   `audio.dual` при этом не переключается, а `audio.codec` применился с задержкой
   (проверено: значение в конфиге изменилось только позже). Перезапуск стримера
   (`restart-streamer`) на выбор кодека не повлиял. Вывод для диагностики: после
   записи настроек нужно ПЕРЕЧИТАТЬ конфиг и сверить значение, а не полагаться на
   код ответа, и отдельно проверять поля, которые камера считает своими.

   На обратный канал эти поля не влияют: дорожка `audio-backchannel` объявлена и
   при `dual: false`, и при `codec: opus`.

17. **Beward (`.11`) требует Digest и по RTSP.** На `DESCRIBE` камера отвечает
   `401` с `WWW-Authenticate: Digest realm="BWD Streaming"`. Basic не подходит —
   из-за этого детектор обратного канала всегда показывал «нет» на домофоне,
   хотя двусторонний звук в его родном приложении работает. Детектор теперь умеет
   Digest (общий код с HTTP-устройствами — `httpdigest.Authorize`). Учётные данные
   в базе для `.11` камера не принимает (401 и с Digest, и с Basic) — нужен
   верный пароль, тогда признак можно будет проверить.
18. **Скорость PTZ — это `Velocity` в `ContinuousMove`, а не отдельная
   настройка.** Камеры парка разгоняются резко: при скорости 1,0 и шаге 400 мс
   навести камеру с телефона точно было невозможно. В мобильном приложении
   темп снижен до 0,2 и добавлен выбор (0,2 / 0,4 / 0,7) при шаге 250 мс; зум
   замедлен вдвое сильнее движения. В веб-интерфейсе скорость уже была 0,4, и
   там есть ползунок длительности шага.

**Техдолг, который остался осознанно:** кнопка двусторонней связи в
веб-интерфейсе (`/cameras/{id}/audio/talk/*`) всё ещё работает через публикацию
кусков PCM в go2rtc — то есть после миграции не работает. Её нужно перевести
на тот же механизм, что в мобильном приложении (микрофон браузера по WebRTC в
backchannel камеры) или удалить чанк-механизм вместе с ffmpeg-сессией.

10. **Веб-интерфейс и API go2rtc открыты в локальной сети** (порт 1984):
   так было и с MediaMTX (HLS 8888 без пароля). Закрывать его надо вкупе с
   проксированием `/mse/` и `/webrtc/` из nginx, иначе операторский
   браузер перестанет смотреть. Оставлено как задача — наружу порт не
   публикуется, доступ ограничен локальной сетью.

## Транспорты просмотра: MSE вместо HLS (2026-10-05)

В **браузере** HLS убран полностью. Причины: он был нужен только MediaMTX
(не умел задержку меньше секунды), сегменты собирались под каждого зрителя
— отсюда холодный старт до 13 секунд — и добавлял ~200 строк прокси
с переписыванием плейлистов.

Теперь браузер получает поток двумя способами:

| Транспорт | Где используется | Особенности |
|---|---|---|
| **MSE** | основной, а также в сетке камер | WebSocket поверх TCP, без UDP; стартует мгновенно |
| **WebRTC** | когда нужна минимальная задержка | ICE/DTLS/SRTP, требует доступного UDP |

Плеер пробует оба: WebRTC первым (или MSE первым в сетке — дешевле),
при неудаче переходит ко второму. Если доступного UDP нет, MSE работает
в любом случае — резервный путь всегда есть.

**Звук теперь внутри основного потока**: go2rtc перекодирует G.711 в Opus
на лету для того, кто слушает. Отдельный AAC-поток (`audioUrl`) и
проксирование HLS-звука больше не нужны. Поток `<id>_audio` остался
только для аудиодетекции (её читает YAMNet по RTSP).

**HLS оставлен для нативных клиентов.** Мобильное приложение (ExoPlayer,
AVPlayer) MSE не умеет, а WebRTC требует отдельной библиотеки. Приложение
берёт HLS по привычному адресу
`/api/v1/cameras/{id}/hls/index.m3u8?token=` — бэкенд сам ходит за плейлистом
и сегментами к go2rtc (`/api/stream.m3u8?src=`) и переписывает ссылки,
чтобы токен авторизации оставался нашим. Отдельный порт HLS не нужен:
go2rtc отдаёт его по API-порту (проверено: `hls.listen` в конфиге 1.9.14
игнорируется). Проверено на живом: плейлист → playlist.m3u8 → segment.ts,
все ответы 200.

Снапшот камеры без JPEG-эндпоинта берётся теперь у go2rtc
(`/api/frame.jpeg?src=`) вместо разбора HLS-плейлиста через ffmpeg.

## Порядок работ

1. Конфиг и инфраструктура: `config.go` (`GO2RTC_API`, `GO2RTC_RTSP`,
   `GO2RTC_PUBLIC`), сервис в `docker-compose.yml` вместо `mediamtx`.
2. `camera_service.go`: регистрация, обновление, удаление потоков.
3. `camera_status_monitor.go`: список потоков и удаление сирот.
4. `handlers/streams.go`: URL для браузера (MSE и WebRTC), HLS — только для
   нативных клиентов (прокси плейлиста и сегментов на привычный путь).
   WebRTC (путь `/webrtc/<id>/whep` сохраняем — go2rtc тоже WHEP).
5. `audio_service.go`: вместо внешнего ffmpeg + публикации — поток
   `ffmpeg:...#audio=aac`; канал `_talk` заменяется backchannel-источником.
6. `nginx.conf`: `/webrtc/` → go2rtc с переписыванием пути.
7. Плеер webui: MSE и WebRTC, HLS из браузера убирается (hls.js удалён из
   зависимостей).
8. Проверка на живом, затем удаление MediaMTX и его конфига.

## Риски

- Порты: у go2rtc `8554` (RTSP), `1984` (API, WebUI, MSE и HLS по тому же
  порту), `8555` (WebRTC). Отдельного HLS-порта у go2rtc 1.9.14 нет, а
  MediaMTX занимал `8888` — после перехода его надо было освободить.
- MSE требует WebSocket-проксирования (`/api/ws`).
- Микрофон браузер даёт только по HTTPS.
