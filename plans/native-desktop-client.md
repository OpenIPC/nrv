# Нативный клиент для рабочих мест (Qt 6)

План полноценного клиента видеостены для Windows и Linux. Заменяет
оболочку WPF + WebView2 из `docs/DESKTOP.md`: та работает только под
Windows, а WebView2 в Astra Linux отсутствует.

## Задача

Клиент для дежурного оператора и для видеостены. Требования, по которым
принимались решения:

- **Видеостена на несколько мониторов.** На каждом мониторе — своя
  раскладка: сетка камер (4×4, то есть 16 потоков) либо план помещения
  с метками. Раскладки переживают перезапуск.
- **Планы помещений** поверх стены: подложка этажа и метки устройств.
- **Тревожные уведомления** — то, ради чего нативный клиент и нужен:
  они не должны уводить оператора с полноэкранной стены.
- **Платформы:** Windows x64 и Linux — Debian, Ubuntu, Astra Linux 1.7.
- Клиент полнофункциональный: кроме стены — СКУД, PTZ, архив, звук,
  настройки и пользователи.

## Почему Qt 6 + QML + GStreamer

| Вариант | Чем не подошёл |
|---|---|
| Обёртка WPF + WebView2 | Только Windows; WebView2 в Astra нет |
| Tauri / WebKitGTK | В WebKitGTK нет аппаратного декодирования H.264 — 16 потоков не поедут |
| Avalonia + LibVLC | Годится, но сетка из нативных поверхностей поверх GL-сцены даёт меньше контроля над синхронизацией и приоритетом ячеек |
| **Qt 6 + QML + GStreamer** | Выбран: аппаратное декодирование (VAAPI в Linux, D3D11VA в Windows), рендер в общей GL-сцене, окно на каждый монитор из коробки |

**Лицензии.** Qt — LGPLv3 (динамическая линковка, обязательств раскрытия
своего кода нет), GStreamer — LGPL. Плагины под GPL (кодеки x264/x265)
в поставку не берутся: кодирование на клиенте не нужно, камеры отдают
готовый H.264.

## Как идёт видео

Основа — **RTSP-субпоток из go2rtc** (наружу отдаёт nginx на `9784`):
задержка около секунды, но 16 потоков он тянет легко и предсказуемо.

- Декодирование аппаратное: `vaapidecodebin` / `d3d11h264dec`.
- Кадры отдаются в Qt через `appsink` → `QVideoFrame` → `QVideoSink`,
  а показываются обычным `VideoOutput` в QML. Это штатный путь Qt 6
  Multimedia, без собственного рендера на первом этапе.
- **Пул декодеров.** Число живущих декодеров ограничено (например, 20).
  Когда камер больше, чем ячеек на экране, приоритет у видимых: ячейка,
  ушедшая на другой монитор или скрытая, освобождает декодер. Без этого
  40 камер в профиле убивают GPU.
- Ячейка без потока показывает снимок `GET /cameras/{id}/snapshot` —
  оператор видит не чёрный прямоугольник, а последнюю картинку.

WebRTC остаётся для одиночного режима: задержка меньше секунды нужна при
PTZ и разговоре. Реализуется позже и отдельно (`webrtcbin`).

**Факты проверки (2026-10-07).**

- Декодер выбирается **с проверкой наличия**: `d3d11h264dec` (Windows) или
  `vaapidecodebin` (Linux), а если их нет в сборке GStreamer — программный
  `avdec_h264`. Раньше аппаратный выбирался безусловно: в сборке без
  `vaapidecodebin` конвейер не собирался вообще, и ни одна ячейка не
  открывалась при живом потоке (`no element "vaapidecodebin"`; проверено
  в контейнере Debian 13 с установленным `gstreamer1.0-vaapi`).
- Если аппаратный декодер есть, но не поднимается (нет устройства VAAPI,
  драйвер видеокарты, удалённый рабочий стол), поток один раз
  перезапускается программным декодером — иначе ячейка оставалась пустой.
- Поддерживается только **H.264**: конвейер видео —
  `rtspsrc ! rtph264depay ! h264parse`. Камеры, отдающие HEVC (в парке
  `.87` — 4К HEVC в основном потоке), в полноэкранном режиме не
  показываются: `Internal data stream error`. Отдельная задача — выбор
  депайлоадера и декодера по кодекам потока.

## Планы помещений

Сервер уже отдаёт всё нужное: `GET /acs/plans`, `GET /acs/plans/{id}/image`
и точки с координатами **в долях от подложки** (`x`, `y` от 0 до 1) и
видом `camera`, `door`, `controller`, `reader`.

Доли, а не пиксели — значит клиент пересчитывает их сам, зная размер
подложки, и план не «съезжает» при замене снимка этажа. Метка камеры
кликабельна: открывает камеру в полноэкранном окне.

## Тревоги

Первоначальный замысел был WebSocket (`GET /api/v1/ws?token=<jwt>`), но
при реализации канал сделан потоком SSE — см. раздел «Тревоги — сделано»
ниже: канал нужен односторонний, и SSE не требует ни библиотеки на
сервере, ни отдельного модуля Qt в поставке клиента.

Осталось из задуманного: звук тревоги, системные уведомления и события
о состоянии каналов (камера пропала, камера вернулась).

Системные уведомления: Windows — через центр уведомлений, Linux — через
D-Bus (`org.freedesktop.Notifications`). Они вторичны: главное — показ
внутри стены, потому что системное уведомление на дежурной машине легко
пропустить.

## Права

Права те же, что и в веб-интерфейсе: клиент входит по JWT, читает
`GET /auth/me` и прячет недоступное (поворот, разговор, открытие двери,
настройки). Напоминание из основного README: интерфейс лишь скрывает, а
**защита — проверка на сервере**, поэтому клиент не может и не должен
обходить отказы.

## Хранение профилей стены

Первый вариант — локально (`QSettings` + JSON в профиле пользователя):
работает без доработок сервера. Второй шаг — `GET/PUT
/api/v1/wall/profiles`, чтобы раскладка дежурной смены была одинаковой
на нескольких машинах.

## Этапы

| Этап | Что делаем | Проверка |
|---|---|---|
| **0. Замер** | Окно с 16 потоками на целевом железе под Astra и Windows | Загрузка GPU/CPU, память, задержка |
| **1. Каркас** | CMake, QML-окна, вход по JWT, список камер, одна камера по RTSP | Играет живой поток |
| **2. Стена** | Сетка 4×4, профили, пул декодеров, снимок вместо пустой ячейки | 16 потоков держатся |
| **3. Планы** | Подложка этажа, метки из точек плана, переход в камеру | Метки на своих местах |
| **4. Тревоги** | Поток событий на сервере (SSE), подсветка ячейки, карточка | Тревога видна на стене |
| **5. Управление** | СКУД (открытие двери), PTZ, архив, разговор | По правам учётной записи |
| **6. Администрирование** | Настройки, пользователи и права | Совпадает с веб-интерфейсом |
| **7. Поставка** | Windows self-contained, `.deb` для Debian/Ubuntu/Astra, автозапуск | Установка без интернета |

Этапы 2 и 3 можно менять местами: план помещения нужен дежурному чаще,
чем 16 потоков разом.

### Windows — сделано

Первый шаг решили делать под Windows, и он готов:

- в сборке есть ветка Windows: GStreamer из установщика MSVC не оставляет
  `pkg-config`, поэтому путь берётся из `GSTREAMER_ROOT`, а при запуске
  приложение само выставляет `GST_PLUGIN_PATH` и `PATH` на папки рядом
  с исполняемым файлом — поставка переносимая, GStreamer на дежурной
  машине не нужен;
- `client/deploy/windows/deploy.ps1` собирает поставку: клиент, интерфейс,
  библиотеки Qt (`windeployqt`), библиотеки и плагины GStreamer; заодно
  проверяет, что обязательные плагины и аппаратный декодер на месте;
- сборка автоматизирована в `.github/workflows/client-windows.yml`
  (Qt 6.7.2 + GStreamer 1.26.5 MSVC, запуск без графической сессии как
  проверка, архив артефактом);
- версия GStreamer выбрана по наличию установщиков MSI: начиная с 1.28
  development-пакет выкладывают только как `.exe`, и разложить его в CI
  без ручных шагов сложнее.

### Планы помещений — сделано (этап 3, клиент)

- Переключатель «Сетка / План» в строке инструментов; кнопка «План»
  появляется только при праве `plans.view`, рядом — список этажей.
- Список берётся из `GET /api/v1/acs/plans`, расстановка — из
  `GET /api/v1/acs/plans/{id}` (поле `points`). Список не содержит точек:
  тянуть расстановку всех этажей при запуске незачем.
- Подложка — `GET /api/v1/acs/plans/{id}/image`. Маршрут **вне** группы
  JWT, поэтому токен идёт параметром (`?token=` или `?jwt=`): элемент
  `Image` в QML не умеет добавлять заголовок `Authorization` к запросу
  картинки — тот же приём, что у снимков камер.
- Координаты точек — **доли от подложки** (0..1). В пиксели их
  пересчитывает клиент по фактическому размеру картинки, поэтому метки
  не съезжают, если этаж перезалили снимком другого размера.
- Цвет метки — состояние устройства: красная — не на связи, серая —
  устройство удалено из системы, синяя — камера, зелёная — дверь или
  контроллер. Состояние берётся на момент открытия плана: обновление
  появится вместе с каналом тревог (этап 4).
- Нажатие на метку показывает карточку с именем и состоянием словами.
  Метка камеры дополнительно открывает её основной поток в отдельном
  полноэкранном окне (выход — Escape или двойное нажатие).
- Режим содержимого и выбранный этаж живут в профиле стены (`wall/content`,
  `wall/plan` в QSettings) — при запуске открывается то, с чем работали.
- Переход в план выгружает сетку: `Loader` уничтожает ячейки, и потоки
  не тянутся впустую, пока их не видно.

Проверено: сборка и загрузка QML без ошибок в контейнере (Qt 6.4.2,
`QT_QPA_PLATFORM=offscreen`), в том числе с заранее выбранным планом в
настройках. На живом стенде **не проверено**: отрисовка подложки,
положение меток при разных размерах окна, открытие полноэкранного окна.

**Урок.** Новый QML-файл, который обращается к синглтонам `Api` или
`Wall`, обязан содержать `import Nvr 1.0`. Без импорта движок выдаёт
`ReferenceError: Api is not defined` на каждую строку, а интерфейс
остаётся пустым — и это видно только в журнале.

### Тревоги — сделано (этап 4)

**Канал на сервере.** Поток `GET /api/v1/events/stream` — Server-Sent
Events. Маршрут вне группы JWT: токен приходит параметром (`?token=`,
`?jwt=` или заголовком), потому что `EventSource` в браузере заголовок
передавать не умеет. Право `events.view` проверяет сам обработчик, а
права берутся из базы с тем же коротким кешем, что у middleware: поток
живёт часами, и отзыв права должен его прекращать.

**Почему не WebSocket, хотя план предполагал `/ws`.** Канал нужен
односторонний — сервер сообщает, клиент слушает. SSE — это обычный
HTTP-ответ: на сервере не нужна библиотека, в поставку клиента не нужен
отдельный модуль Qt (QtWebSockets) со своей библиотекой, а отладка
сводится к `curl -N`. Платой была бы двусторонность, которая тревогам
не нужна; обратные действия (открыть дверь, PTZ) идут обычными запросами.

**Шина.** Пакет `internal/live`: хаб и подписчики. Публикация
неблокирующая — если подписчик не успевает читать, событие для него
пропускается и считается (буфер 64 события). Для тревог это осознанный
выбор: лучше потерять устаревшее событие, чем задержать новые и
затормозить обработку детекций из-за одного зависшего клиента.

**Источники событий:** детекции и звук — из NATS-подписчика (там же
формируется имя камеры, один запрос на событие теперь общий для вебхука
и потока), проходы СКУД — из `POST /api/v1/acs/ingest`.

**Клиент.** `LiveEvents` (C++): разбор SSE, автоматическое
переподключение через 5 секунд, сторож тишины на 60 секунд — сервер
присылает комментарий каждые 20 секунд, поэтому полная тишина означает
мёртвое соединение, о котором сокет может и не сообщить. Карточка
тревоги (`AlarmCard.qml`) — поверх стены, не забирает фокус; ячейка
камеры мигает и подписывается «ТРЕВОГА» 25 секунд; состояние связи
видно значком в строке инструментов.

**Проверено на живом сервере** (стенд с камерами парка):

- поток открывается по токену, без токена — `401`;
- событие, отправленное в NATS (`cameras.<id>.detection`), доходит до
  клиента: в журнале `тревога: detection Камера 192.168.1.87 car`;
- тесты шины (`go test -race ./internal/live/`) проходят.

**Урок.** Обёртка `http.ResponseWriter` в middleware скрывает
возможности настоящего ответа: из-за неё поток отвечал «сервер не умеет
отдавать поток», хотя лежащий под обёрткой ответ всё умеет. Лечится
методом `Flush` и `Unwrap` у обёртки плюс `http.NewResponseController`
в обработчике вместо приведения типа. Правило: если middleware
оборачивает ответ, она обязана пробрасывать `Flush` и `Unwrap`.

**Не сделано:** звук тревоги и системные уведомления, состояние каналов
(камера пропала или вернулась) как источник событий, живое обновление
меток на плане, перевод веб-интерфейса на этот же поток.

### Управление камерой и звук — сделано (этап 5, часть)

**Двойное нажатие по ячейке** открывает камеру на весь экран основным
потоком (в сетке — субпоток, в развороте качество важнее числа потоков).
Очистка ячейки переехала из двойного нажатия в меню по правой кнопке:
просмотр и разрушение раскладки не должны быть одним и тем же действием —
на стенде раскладку теряли по неосторожности.

**PTZ.** Пульт появляется, только если камера помечена как поворотная
(`camera.ptz`) и у вошедшего есть право `ptz.control`. Используются
серверные эндпоинты `/cameras/{id}/ptz/move|stop|presets|presets/goto`.
Каждое нажатие — шаг с длительностью (по умолчанию 400 мс): камера
останавливается сама, поэтому оператору не нужно «держать» кнопку, а
оборванная связь не оставляет камеру в движении. Отдельная кнопка
остановки нужна, чтобы прекратить движение раньше или прервать переход
к позиции.

**Звук камеры.** Отдельный конвейер GStreamer:
`rtspsrc → decodebin → audioconvert → audioresample → volume → autoaudiosink`.
Отдельный, а не ветка в проигрывателе: камера может не отдавать аудио
вовсе, и тогда видео должно продолжать работать; кроме того звук нужен
при просмотре одной камеры, а не в сетке из шестнадцати потоков.

**Ключевая тонкость (найдена на живом парке).** `rtspsrc` отдаёт по паду
на каждую дорожку потока (видео и звук), и у `decodebin` **один** вход.
Обычная связка `gst_element_link(rtspsrc, decodebin)` соединяет только
ПЕРВУЮ появившуюся дорожку. Порядок задаёт описание сессии: у части
камер первой идёт звуковая дорожка, у части — видеодорожка (проверено:
`cameras/1`, `cameras/12`, `cameras/16` — звук первым; `cameras/20` —
видео первым). На камерах второго вида звук не открывался вовсе —
это и была причина жалобы «в Windows нет звука».

Как исправлено: к `decodebin` подключается только дорожка с
`media=audio` (отбор в обработчике `pad-added` у `rtspsrc`). Видеодорожку
не подаём вовсе — её декодирование на 4К отняло бы процессор у стены.
На случай не-звукового пада оставлена заглушка `fakesink`: дорожка без
получателя останавливает конвейер (`streaming stopped, reason not-linked`).

**Факт с живой камеры** (канал 2, «Камера 192.168.1.12»): поток отдаёт
Opus 48 кГц стерео; цепочка `rtpopusdepay → opusdec → audio/x-raw S16LE`
подтверждена через `gst-launch` в контейнере. У другой проверенной
камеры микрофона нет (`audio_settings.has_microphone = false`), поэтому
кнопки звука и разговора показываются только при наличии возможностей —
иначе они сбивали бы с толку.

**Двусторонняя связь.** Микрофон захватывает GStreamer
(`autoaudiosrc → audioconvert → audioresample → audio/x-raw S16LE 8 кГц
моно → appsink`), порции уходят на `POST /cameras/{id}/audio/talk/chunk`.
Кодированием занимается сервер: он поднимает ffmpeg, кодирует PCM в
G.711 и публикует звук в обратный канал камеры (ONVIF/RTSP backchannel).
Кнопка работает **удержанием**: открытый микрофон без присмотра — это
запись всего, что происходит в диспетчерской.

**Почему не Qt Multimedia.** Модуль намеренно не подключён: его библиотека
требовалась при запуске, но отсутствовала в поставке, и приложение
падало, не показав окна. GStreamer уже есть в поставке и умеет звук
и на Windows, и на Linux.

**Диагностика.** Устройство вывода можно подменить переменной
`NVR_AUDIO_SINK` (например, `fakesink`): так проверяют, доходит ли звук
до клиента, на машине без звуковой карты.

**Проверено** (2026-10-07, контейнер Debian 13, GStreamer 1.26.2): сборка,
загрузка QML без ошибок, выбор звуковой дорожки на живых камерах парка
через `9784` (`cameras/1`, `12`, `16`, `20`) — звук декодируется и доходит
до приёмника. **Не проверено:** вывод звука на устройство и разговор
вживую — в рабочем окружении нет звуковой карты и микрофона, нужен стенд.

### Несколько экранов — сделано (этап 2, вариант А)

Решено так: **главное окно** — вход и настройки рабочих мест, а стена
живёт **отдельными полноэкранными окнами, по одному на монитор**.
В настройках выбирают, сколько экранов и какая сетка на каждом;
камеры назначаются прямо в окне стены (ячейка → камера в списке).

- Модель: `WallScreen` — один экран (монитор, сетка, назначения, вид
  содержимого, положение окна), `WallProfile` — список экранов и запись
  в QSettings. Экраны — живые объекты, а не копии: правка сетки
  в настройках видна в окне стены сразу, без перезапуска.
- Окна: `WallWindow` — окно одного экрана. Номер монитора проверяется
  при открытии: если экран отключили, окно открывается на основном, иначе
  оно оказалось бы вне рабочего стола. Фактический монитор пишется
  в журнал отдельно от профильного — по этой записи разбирают
  «окно уехало не туда».
- Миграция: прежний одноэкранный профиль (`wall/columns`, `wall/assignments`
  и прочие ключи) переносится в первый экран, старые ключи удаляются.
  У людей уже собрана стена, и терять её при обновлении нельзя.
- Тревоги показываются на том экране, где эта камера выведена; события
  по камерам, которых нет ни в одной раскладке, показывает первый экран —
  иначе такое событие не увидел бы никто.
- Проверено в контейнере (offscreen, один монитор): профиль из двух
  экранов открывает два окна с сетками 3×3 и 2×2, окно с монитором 1
  встаёт на доступный монитор 0, перенос старого профиля выполняется.
  **Не проверено:** настоящие два монитора и полноэкранный режим на стенде.

### Поставка под Debian 13 — сделано (этап 7, часть)

- Сборка в контейнере **Debian 13 (trixie)** — `deploy/Dockerfile.debian13`.
  Это не формальность: в Debian 13 Qt 6.8 и GStreamer 1.26, а проверочный
  контейнер был на Debian 12 (Qt 6.4, GStreamer 1.22). Клиент, собранный
  и проверенный на одних версиях и поставленный на другие, в этом проекте
  уже давал ложные выводы («звука нет, хотя всё установлено»).
- `deploy/linux/deploy.sh` собирает два артефакта: **`.deb`** (зависимости
  тянутся из репозитория) и **tar.gz** (переносимая копия, библиотеки из
  системы). Библиотеки Qt и плагины GStreamer внутрь пакета **не**
  кладутся — в отличие от поставки под Windows: версии в дистрибутивах
  расходятся, и вложенные копии сделали бы пакет работающим только там,
  где он собран.
- `gstreamer1.0-vaapi` в Recommends, а не в Depends: без аппаратного
  декодирования клиент работает, только грузит процессор сильнее.
- Клиент ищет интерфейс рядом с собой, а в пакете — в
  `/usr/share/nvr-wall/qml` (в `/usr/bin` данные держать нельзя).
- Проверено в чистой Debian 13: пакет устанавливается со своими
  зависимостями, клиент запускается из `/usr/bin` и грузит интерфейс
  из `/usr/share` (Qt 6.8.2, GStreamer 1.26.2).
- Ветка сборки `.github/workflows/client-linux.yml` делает то же и заодно
  **ставит пакет в чистую Debian 13 и запускает клиент** — так ловятся
  и неверные зависимости, и потерянный интерфейс.
- Не сделано: значок приложения (в поставке своего набора нет),
  автозапуск и установка без доступа к репозиторию.

## Что уже проверено

Проверки шли в контейнере на Debian 12 (Qt 6.4.2, GStreamer 1.22), потому
что в рабочем окружении Qt и GStreamer нет, а `sudo` требует пароль.

- **Сборка проходит** (`client/deploy/Dockerfile.build`).
- **Интерфейс грузится** без ошибок QML — проверено запуском без дисплея
  (`QT_QPA_PLATFORM=offscreen`).
- **Живой поток принимается.** Тем же конвейером, что в клиенте, снято
  50 кадров с камеры через RTSP-прокси:
  `rtspsrc → rtph264depay → h264parse → avdec_h264 → videoconvert → RGB`.
- **RTSP-прокси на 9784 требует логин и пароль** (`EXTERNAL_RTSP_USER` и
  `EXTERNAL_RTSP_PASS`, по умолчанию `viewer`). Клиент их передаёт в
  адресе потока; без них он получил бы отказ.
- **Видео идёт не через порт веб-интерфейса, а через `9784`** — при
  внешнем доступе его надо пробросить отдельно. Проверено: с адреса
  `83.243.73.86` порт `8080` (API) открыт, а `9784` — нет; клиент с таким
  адресом сервера входит и видит список камер, но картинки нет
  («Connection refused» в журнале). В локальной сети указывать
  `192.168.1.111`, а не внешний адрес.
- **`/cameras/{id}/stream` клиенту не годится**: отдаёт либо
  `rtsp://localhost:8554/...` (внутренний адрес go2rtc), либо адрес самой
  камеры. Клиент пока строит адрес сам от настроек медиасервера — это
  временное решение до серверного эндпоинта с проверкой прав.
- **В Qt 6.4 `VideoOutput.videoSink` — только для чтения**, подменить
  приёмник нельзя. Поэтому кадры принимает свой элемент `VideoItem`
  (текстура в сцене Qt Quick), а не `VideoOutput`.
- Кадры передаются в RGB: конвертацию делает GStreamer — она у него
  векторизована, и на шестнадцати потоках это заметно.

Не проверено (нужна машина с графической сессией): отрисовка на экране,
ввод пароля через форму, синхронная работа 16 потоков, аппаратный VAAPI
(в контейнере проверялся `avdec_h264`).

## Отрисовка кадра: осторожно с узлами сцены

Первый вариант элемента отрисовки (`QSGSimpleTextureNode` в своём
`updatePaintNode`) ронял приложение на Windows: нарушение доступа внутри
`Qt6Quick.dll` через пару секунд после открытия окна. Ошибка не оставляла
сообщений — процесс просто исчезал; нашлась только по перехвату
необработанных исключений с именем модуля.

Сейчас кадр рисует `QQuickPaintedItem` (`QQuickPaintedItem` сам владеет
текстурой и очередью отрисовки). Быстрый путь — свои узлы сцены, кадры
без лишних копирований, аппаратные буферы — вернём отдельной задачей,
когда сетка заработает на стенде и появятся замеры.

Правило на будущее: любой свой узел сцены проверять на стенде под
Windows отдельно, а в клиенте держать обработчик необработанных
исключений — без него такие падения не диагностируются.

## Проверка на стенде

Собирать и запускать нужно там, где есть Qt 6 и GStreamer; в этом
рабочем окружении их нет, а `sudo` без пароля недоступен — здесь
проверяется только компиляция (в контейнере).

Необходимые пакеты (Debian 12 / Ubuntu 24.04 / Astra 1.7):

```
qt6-base-dev qt6-declarative-dev qt6-multimedia-dev qt6-tools-dev
libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev
gstreamer1.0-plugins-base gstreamer1.0-plugins-good gstreamer1.0-plugins-bad
gstreamer1.0-libav gstreamer1.0-vaapi
```

## Риски

| Риск | Что делаем |
|---|---|
| В Astra нет части пакетов GStreamer | Проверить на живом Astra до этапа 2; при отсутствии — сборка плагинов из исходников или переход на `avdec_h264` (программный) для субпотока |
| 16 потоков 1080p не тянут GPU | Сетка использует субпоток (704×576 или 640×360); основной поток — только в полноэкранном режиме |
| Утечки памяти в GStreamer-конвейерах | Один конвейер на ячейку, обязательный переход в `NULL` при смене камеры; проверка `GST_TRACERS=leaks` |
| Разные версии Qt на стенде | Сборка под Qt 6.x из репозитория Astra, поставка зависимостей в `.deb` |
