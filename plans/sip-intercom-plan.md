# SIP-домофония: вызовы с панели в приложения

План интеграции SIP-домофонии в сервер, веб-интерфейс, мобильное приложение
и десктоп-клиент. Документ фиксирует решения и причины — чтобы не выбирать
заново то, что уже проверено или отклонено владельцем.

## Задача

- Вызывная панель **Beward DS07P-LP** звонит, и вызов приходит на мониторы,
  мобильные приложения и десктопы.
- Камеры OpenIPC с динамиком и микрофоном тоже могут быть вызывными
  панелями (у них есть раздел `sip` с кнопкой вызова).
- Видеомониторы (видеодомофоны) участвуют в вызовах как обычные абоненты.
- Состав участников вызова **настраивается в веб-интерфейсе**: группа
  вызова, куда абонентов добавляют и убирают.
- Разговор двусторонний: видео панели видно, звук идёт в обе стороны,
  дверь открывается из интерфейса.

## Решения

### 1. Asterisk ставим свой, образ 18-й ветки

```
andrius/asterisk:18    →    Asterisk 18.26.4
```

Причина — **старый драйвер `chan_sip`**. Панель Beward и SIP-монитор с новым
драйвером `chan_pjsip` работают некорректно, поэтому нужен именно старый.

Проверено фактически (запуском контейнеров, не по документации):

| Образ | Версия | `chan_sip` | `chan_pjsip` |
|---|---|---|---|
| `andrius/asterisk:20` | 20.20.1 | нет | есть |
| `andrius/asterisk:18` | 18.26.4 | **есть** | есть |
| `andrius/asterisk:latest` | 22.10.1 | нет | есть |

Обоих драйверов требует и вторая причина: **`chan_sip` не умеет WebSocket**,
а приложения (браузер, мобильное, десктоп) подключаются через WebRTC — это
SIP over WebSocket, который поддерживает только `chan_pjsip`
(`res_pjsip_transport_websocket`). То есть одним старым драйвером обойтись
нельзя: устройства без него не работают, а приложения без нового.

Драйверы уживаются в одном Asterisk. Порты разносим:

| Драйвер | Транспорт | Порт | Кто использует |
|---|---|---|---|
| `chan_sip` | UDP | `5060` | панель, камеры, мониторы |
| `chan_pjsip` | WebSocket | `8089` | браузер, мобильное, десктоп |
| RTP | UDP | `10000-10100` | все (сужен диапазон, чтобы не открывать сотни портов) |

> Риск: ветка Asterisk 18 завершает поддержку. Для домашней системы это
> приемлемо. Если позже понадобится свежая база — можно собрать свой образ
> на 20-й ветке с включённым `chan_sip`.

### 2. Видео звонка идёт не через SIP

Панель и камеры и так отдают поток в go2rtc. Окно входящего вызова открывает
этот поток (как сейчас открывается камера), а голос идёт по SIP. Причина:
видео в SIP требует согласования кодеков и passthrough через Asterisk, а у
нас уже есть проверенная дорога RTSP → WebRTC. Звук при этом двусторонний —
он у нас тоже работает (обратный канал ONVIF).

### 3. Номера: каждому приложению свой

Владелец: «номера у приложений естественно разные». Значит каждое мобильное
приложение, десктоп и браузерное рабочее место получают **отдельный номер**
и свои учётные данные. Это позволяет видеть в журнале, кто ответил, и
отключать конкретное устройство, не задевая остальные.

### 4. Группа вызова — настраиваемая, по умолчанию «все сразу»

Звонок с панели уходит в группу: все её участники звонят одновременно,
отвечает первый. Состав группы оператор задаёт в интерфейсе — добавляет и
убирает абонентов. Стратегия (`все сразу` / `по очереди`) и время звонка —
параметры группы.

### 5. Открытие двери — из интерфейса, двумя путями

- DTMF `123` в разговоре (так настроена панель: замыкание реле + сброс вызова);
- напрямую через наш адаптер СКУД `backend/internal/service/acs/beward.go`
  (`alarmout_cgi`) — работает и когда разговор не идёт.

Наша база — источник правды по открытиям: панель подключена к кнопке выхода
Z5R, и по журналу контроллера источник не отличить (см.
`/memories/repo/beward-intercom.md`).

## Модель данных (черновик)

| Таблица | Поля | Назначение |
|---|---|---|
| `sip_accounts` | id, number, password, kind (`panel`/`camera`/`monitor`/`softphone`), device_id (камера/контроллер), display_name, enabled | абоненты: устройства и приложения |
| `sip_groups` | id, name, strategy (`all`/`sequential`), ring_seconds, enabled | группы вызова |
| `sip_group_members` | group_id, account_id, position | состав группы |
| `sip_rules` | id, source_account_id, group_id, enabled | кто звонит → какая группа |
| `sip_calls` | id, started_at, answered_at, ended_at, from_number, to_account_id, result (`answered`/`missed`/`rejected`), talk_seconds | журнал звонков |

Отдельного раздельного хранения паролей не делаем: они и так лежат в базе,
доступ к которой есть только у сервера. В интерфейсе они показываются так же,
как секреты камер — не раскрываются повторно.

## Генерация конфигурации Asterisk

Источник правды — наша база, конфиги Asterisk собираются из неё:

- `sip.conf` — устройства (`chan_sip`);
- `pjsip.conf` — приложения (транспорт WS, эндпоинты, auth, aor);
- `extensions.conf` — контексты и группы вызова: `Dial(SIP/101&SIP/102,30)`
  для «все сразу», последовательные `Dial` с таймаутом для «по очереди»;
- `http.conf` — включение WebSocket для приложений.

После перезаписи — `asterisk -rx "sip reload"`, `"pjsip reload"`,
`"dialplan reload"`. Так установка остаётся переносимой: в другом доме
оператор заводит свои устройства, а не правит конфиги руками.

### Панель настраивается программно — это важно для интерфейса

Beward отдаёт SIP-настройки как `key=value` через CGI, то есть наш сервер
может **сам** перевести панель на нужный адрес, а не просить оператора
ходить в её веб-интерфейс:

```bash
# чтение
curl --digest -u admin:ПАРОЛЬ "http://192.168.1.11/cgi-bin/sip_cgi?action=get"
# запись
curl --digest -u admin:ПАРОЛЬ \
  "http://192.168.1.11/cgi-bin/sip_cgi?action=set&RegServerUrl1=192.168.1.111"
```

Полезные факты из его ответа:

| Параметр | Значение | Что значит |
|---|---|---|
| `AccNumber1`, `AccPassword1` | `101`, `changeme_panel_101` | счёт и пароль (шаблон: `changeme_panel_<номер>`) |
| `Acc1ContactNumber1`, `...2` | `200`, `111` | контакты вызова — их удобно считать **именами групп** |
| `DtmfMode1` | `info` | сигналы кнопок идут через SIP INFO, а не тонами |
| `NatEnable1` | `on` | на панели включён NAT (учесть, если голос пойдёт в одну сторону) |

Из-за `DtmfMode=info` абоненту панели в Asterisk задан `dtmfmode=info`:
при несовпадении цифра «открыть дверь» до сервера не доходит.

### Камеры Majestic: настройки SIP применяются только после перезагрузки

Записанный в конфиг раздел `sip` не запускает SIP-клиент на лету: от камеры
не приходит ни одного SIP-пакета, пока её не перезагрузить.
Перезагрузка — **POST** `/cgi-bin/restart.cgi` (GET отдаёт страницу с
подтверждением и ничего не делает). Сборка проверенной камеры —
SigmaStar SSC338Q, ядро 4.9.84.

Панель Beward, в отличие от камеры, новый сервер подхватила без перезагрузки.

### Правила групп в dialplan

Контакты панели (`200`, `111`) сделаны именами групп вызова; правило
подключается из `accounts/extensions_accounts.conf`:

```
exten => 200,1,NoOp(Вызов от ${CALLERID(num)} в группу «Все»)
 same => n,Dial(SIP/109,25)
 same => n,Hangup()
```

Пока в группе одна камера: этого достаточно, чтобы видеть, что путь
«панель → группа → абонент» работает. Номера приложений (`3XX`) добавятся
сюда, когда появятся WebRTC-абоненты.

## Выполнено: этап 3 — приложения по WebRTC (2026-10-09)

Приложение-абонент `300` зарегистрировалось из браузера и приняло входящий
вызов **в сигнальной части**:

```
ЗАРЕГИСТРИРОВАН на сервере
ВХОДЯЩИЙ вызов от sip:anonymous@anonymous.invalid
Вызов не состоялся: User Denied Media Access   ← микрофон недоступен
```

Список контактов на сервере подтверждает регистрацию:

```
Contact: 300/sip:...@172.20.0.5:38796;transport=ws   Avail
```

Последняя строка — про микрофон, а не про сервер: во встроенном браузере
рабочего окружения нет доступа к звуковой карте. Проверка звука в обе
стороны — за оператором, в обычном браузере (см. ограничения ниже).

### Четыре грабли, найденные на живом

1. **WebSocket живёт на HTTP-порту Asterisk (8088), отдельного порта нет.**
   `bind` в транспорте pjsip на это не влияет: транспорт WS обслуживает
   встроенный HTTP-сервер, порт задаётся в `http.conf`. Проверено: с
   `bind=0.0.0.0:8089` порт 8089 не слушался, а подключение шло на `8088/ws`.
2. **Подпротокол `sip` забирает тот драйвер, кто загрузился первым** — а по
   алфавиту это `chan_sip`. Регистрация приложения попадала в старый драйвер
   и падала с «Wrong password». Лечится `preload => res_pjsip_transport_websocket.so`
   в `modules.conf`.
3. **Этот модуль зависит от ARI** (`res_ari`): без включённого `ari.conf`
   он «declined to load». ARI всё равно нужен для журнала звонков, так что
   включён по делу, а не ради обхода.
4. **Имя AOR должно совпадать с именем endpoint.** С `aors=aor300` при
   endpoint `300` регистрация отвечала `404 Not Found`, в журнале:
   `find_registrar_aor: AOR '' not found for endpoint '300'`. После
   переименования AOR в `300` регистрация прошла сразу.

### Проксирование WebSocket через интерфейс

Наружу порт 8088 не открываем: nginx веб-интерфейса проксирует `/ws`
(`webui/nginx.conf`), поэтому приложение подключается к
`ws://адрес:3001/ws`. Проверено: `101 Switching Protocols` и напрямую, и
через интерфейс.

### Ограничение браузера: звонок требует HTTPS

Браузер отдаёт микрофон только на защищённой странице (HTTPS) или на
`localhost`. Значит звонки из **веб-интерфейса** заработают лишь после
подключения сертификата; для мобильного приложения этого ограничения нет
(там микрофон доступен приложению). Это нужно учесть при реализации
страницы «Домофония»: либо сертификат, либо звонки только в приложении и
на десктопе.

### Тестовый клиент

`webui/public/sip-test.html` + локальная копия библиотеки
`webui/public/jssip.min.js`. Библиотеку положили рядом, а не на CDN:
сервер может стоять без интернета, и внешняя ссылка тогда не загрузится
(на этом уже споткнулись). Пароль абонента задаёт установка, в репозитории
его нет.

```
101 panel    sip    на связи
109 camera   sip    на связи
300 softphone pjsip на связи
```

План набора после сборки из базы (правило «200 → все устройства»):

```
'200' =>  1. NoOp(Вызов от ${CALLERID(num)} в группу Все устройства)
          2. Dial(SIP/101&SIP/109&PJSIP/300,30)
          3. Hangup()
```

**Грабли этого этапа (все — на живом Asterisk 18)**

1. **Команды `pjsip reload` в ветке 18 нет.** На `Action: Command` с этой
   строкой сервер отвечает «No such command 'pjsip reload'». Перезагрузка
   абонентов приложений делается через `module reload res_pjsip.so`.
   Ошибка коварная: команда «не найдена», но конфигурация абонентов при этом
   остаётся прежней, а в интерфейсе всё сохранено.
2. **Ответ AMI на команду не такой, как в документации.** В этой сборке
   вывод приходит строками `Output: …` и заканчивается пустой строкой, без
   маркера `--END COMMAND--`. В других сборках встречается старый вид
   (`Response: Follows` + строки до маркера). Поддержаны оба вида: приняв
   первый за «пустой ответ», сервер отдал бы пустой список зарегистрированных
   абонентов и выглядел бы исправным.
3. **Asterisk шлёт события в тот же поток.** После входа приходит
   `Event: FullyBooted`, и он попадает между ответами. Блоки событий надо
   пропускать, иначе разбор уезжает на один ответ назад.
4. **У заголовка таблицы контактов нет номера.** Строка
   `Contact: <Aor/ContactUri...> <Hash...> <Status> <RTT(ms)..>` проходила
   общий разбор и давала абонента «<Aor». Отсекаем по цифре в начале номера.

**Осталось по этапу 2**

- Трубка Dahua (`192.168.1.118`) и Fanvil i501 (`192.168.1.50`) в базе ещё
  не заведены: у них не настроен SIP. Пока в базе три записи — панель,
  камера и приложение.
- Журнал звонков и запись разговоров — не начаты (в плане этап 6).

## Настройка сторонних устройств (проверено 2026-10-09)

Задача: заводить устройства в базе мало — на них ещё нужно прописать наш
сервер. Ниже то, что выяснено на живых устройствах: где это можно делать
программно, а где придётся руками.

### Fanvil i501 (трубки `192.168.1.50` и `192.168.1.179`) — настраивается программно

Отдельного документированного REST API у Fanvil нет, но настройку можно
выполнить по сети — и делается это **импортом файла конфигурации**, а не
записью полей веб-формы.

Инструмент: `scripts/fanvil_set.py` (чтение/запись полей формы) и — основной
путь — серверный модуль `backend/internal/service/fanvil_config.go`.

Как это работает (проверено живьём):

1. **Вход** в веб-интерфейс: `GET /` (ставит cookie) → `GET /key==nonce`
   → `POST /` с `encoded=<логин>:md5(<логин>:<пароль>:<nonce>)`.
2. **Экспорт**: `GET /default_user_config.txt` — текущие настройки в текстовом
   виде (есть также `.xml` и `ncConfig.txt`).
3. **Импорт**: `POST /config.htm` как `multipart/form-data`, поле файла `CONFIG`.
4. **Проверка**: прочитать настройки обратно — устройство отвечает `200` даже
   на непринятый файл, и без обратного чтения «успех» ничего не значит.

Формат файла (из выгрузки самой трубки):

```
<<VOIP CONFIG FILE>>Version:2.0000000000

<SIP CONFIG MODULE>
--SIP Line List--
SIP1 Phone Number       :114
SIP1 Display Name       :Трубка Fanvil i501
SIP1 Register Addr      :192.168.1.111
SIP1 Register Port      :5060
SIP1 Register User      :114
SIP1 Register Pswd      :<пароль>
SIP1 Enable Reg         :1
SIP1 Proxy Addr         :192.168.1.111
```

Что важно знать:

1. **Страница настроек называется `config.htm`.** Её долго не находили,
   потому что имя короче ожидаемого (`configuration.htm`, `autoprovision.htm`,
   `provisioning.htm` → 404). В боковом меню она не показана, хотя в
   `config.js` прошивки присутствует.
2. **Пароль в экспорте замаскирован** префиксом `###` (`###SIP1 Register Pswd`).
   При импорте он пишется обычным значением — иначе в устройстве останется
   старый пароль, и регистрация не пройдёт.
3. **Импорт файла не бьётся о лимит частых входов.** Раньше запись через
   форму линии (148 полей) упиралась в `503 Server Too Busy`: устройство
   ограничивает частые обращения и держит одну сессию. Один POST с файлом
   этой проблемы не создаёт.
4. **Адрес сервера берём только как узел.** Если подставить `PUBLIC_URL`
   целиком (`http://192.168.1.111:8080`), в трубку попадёт адрес веб-доступа,
   и регистрация не пройдёт — проверено.

Проверено на живом: абоненты `114` (трубка .50) и `115` (трубка .179) настроены
из API, настройки применились и подтвердились обратным чтением; обе
зарегистрированы на Asterisk. Для Dahua сервер отвечает понятным отказом
(`501`) — там настройка только в меню устройства.

Дополнительно: `GET /api/v1/sip/accounts/{id}/config-file` отдаёт готовый файл
(кнопка «Скачать файл настроек» на странице «Домофония») — для переноса
настройки вручную, если сеть до устройства недоступна.

Устройство умеет забирать конфигурацию и самостоятельно — по SIP PnP,
DHCP Option 66, Static Provisioning Server или TR069 (протоколы FTP, TFTP,
HTTP, HTTPS; форматы txt, cfg, xml). Это описано в документе «Auto Provision
Description». Такой путь не требует доступа к веб-интерфейсу вовсе, но
требует настроить раздачу адреса автонастройки в сети — на будущее.

### Dahua видеодомофон TI-3430WP (`192.168.1.118`) — настраивается вручную

Открыт только `37777` — проприетарный протокол Dahua; `80`, `443`, `8000`,
`8080` закрыты, HTTP-интерфейса нет. Настроить SIP по сети можно только
через Dahua SDK (`dhnetsdk`/`dhconfigsdk`) — это отдельная интеграция на
C-библиотеках, несопоставимая по объёму с задачей.

Практичный путь выбран и проверен: **SIP настраивается в меню самого
устройства**, а абонент заводится у нас. Устройство зарегистрировалось:
`116/116 192.168.1.118 … OK`, user agent `True IP UAC/3.0 TI-3430WP
V4.520.0.0`.

Отдельный урок из этой проверки: **`Wrong password` в журнале Asterisk не
всегда про пароль.** В журнале было

```
Registration from '<sip:116@192.168.1.111:5060>' failed for '192.168.1.118:5060' - Wrong password
```

при том, что в базе был заведён абонент `115`, а на устройстве набран `116`.
Пароль был верный — не было самого абонента с таким номером. Лечится
приведением номера в соответствие (запись переименована в `116`), а не
поиском ошибки в пароле. Перед разбором «неверного пароля» сверяйте номер
из строки журнала с номером в базе.

## Страница «Домофония»: вкладки и карточка абонента (2026-10-09)

Страница переделана: абонентов может быть много, и держать их вместе
с группами, правилами и настройками сервера в одной простыне неудобно.

| Вкладка | Что на ней |
|---|---|
| **Абоненты** | список с поиском (номер, название, адрес) и фильтром по виду; добавление и удаление; ссылка на карточку |
| **Группы вызова** | состав групп галочками, стратегия обзвона и время |
| **Правила вызова** | какой набранный номер в какую группу звонит |
| **Настройки** | внешний адрес, свои сети, видеозвонки и кодек, время звонка |

**Карточка абонента** (`/intercom/:id`) — отдельная страница: про устройство
нужно знать много, и в строке списка это не показать.

- **Данные телефонии** — то, что видит Asterisk: состояние (`OK (3 ms)`),
  адрес с портом, устройство с версией прошивки и MAC, драйвер.
  Берутся командой `sip show peer <номер>` (для приложений —
  `pjsip show contacts`), а не из нашей базы: только Asterisk знает
  настоящий адрес и версию прошивки.
- **Настройки абонента** — номер, вид, название, пароль, заметка, включён.
- **Уведомления о вызовах** — Telegram, MAX, пропущенные звонки и запись
  видео со звуком. Каналы разделены: панель у калитки и трубка в офисе
  могут уведомлять в разные чаты.
- **Размещение** — коммутатор и порт, по образцу камер (`sip_switch_port`).
  По этой привязке видно питание порта и понятно, куда идти руками.
- **Группы вызова** — в каких группах состоит абонент; у группы виден её
  номер.
- **Действия с устройством** — зависят от производителя: у Fanvil — скачать
  файл настроек или записать его в устройство, у Dahua, OpenIPC и Beward
  кнопка заблокирована с объяснением, где тогда править SIP. Вендор хранится
  у абонента (`sip_accounts.vendor`), а если он не задан — берётся из ответа
  устройства, который видит Asterisk.

## Прямой вызов между абонентами и номер группы (2026-10-09)

Раньше устройства могли звонить **только** в группу по правилу: в секции
`[from-devices]` был общий перехват `_X!`, уводивший любой номер в
`Congestion`. Друг другу абоненты дозвониться не могли, хотя номера у них
есть.

Что сделано:

- Группа получила **собственный номер** (`sip_groups.number`, уникальный
  индекс по непустым). Номер видно и можно править на вкладке «Группы
  вызова», он же генерирует правило в плане набора. Разовая миграция перенесла
  в него номер из правила, если у группы было правило без источника.
- Правило общего вида, дублирующее номер своей группы, при сборке
  **пропускается**: иначе номер группы оставался бы вообще без extension
  (занятым считался бы он сам).
- В `[from-devices]` добавлен **прямой вызов**: `_1XX` → `Dial(SIP/${EXTEN})`
  (устройства), `_3XX` → `Dial(PJSIP/${EXTEN})` (приложения). Он стоит
  **раньше** общего перехвата `_X!`, поэтому набранный номер устройства
  звонит напрямую, а не в группу.

Проверено на живом Asterisk: `dialplan show from-devices` содержит `200`
(группа «Все устройства» → `SIP/114&SIP/116&PJSIP/300&SIP/115`), `_1XX`,
`_3XX` и `_X!`.

Ответ на вопрос «могут ли абоненты звонить друг другу»: до этой правки — нет,
теперь — да, по своим номерам.

## Адрес устройства берётся из регистрации (2026-10-09)

Адрес устройства (`sip_accounts.host`) нужен дважды: чтобы записать настройки
по сети и чтобы сканер отличал уже заведённый домофон от нового. Вписывать его
руками — шаг, который легко забыть, и тогда исправная трубка выглядит
незаведённой.

Теперь сервер узнаёт адрес сам: при открытии карточки абонента берётся
контакт из Asterisk (`Addr->IP` у `sip show peer`, `sip:…@адрес:порт` у
`pjsip show contacts`), из него выделяется адрес (`service.HostFromContact`,
учитывает порт, параметры транспорта и префикс `sip:`) и сохраняется у
абонента. Правило: **свой адрес приоритетнее** — подставляется только когда у
абонента его ещё нет; устройство могло переехать, и вписанное вручную значение
затирать нельзя.

В карточке для этого есть поле «Адрес устройства» с подсказкой
«определяется сам по регистрации»: оно нужно, когда устройство молчит, а в
его веб-интерфейс зайти надо. Пустой адрес при сохранении означает «оставить
прежний» (`host = COALESCE(NULLIF($7, '')::inet, host)`) — иначе правка любого
другого поля карточки стирала бы авто-подставленный адрес.

Проверено живьём: открытие карточек заполнило адреса всем устройствам —
`101 → 192.168.1.11`, `109 → 192.168.1.106`, `114 → 192.168.1.50`,
`115 → 192.168.1.179`, `116 → 192.168.1.118`; у приложения `300` (не на
связи) адрес не ставится, что и правильно.

Настройки сервера **влияют на конфигурацию**: внешний адрес и свои сети
попадают в `accounts/server_settings.conf` (подключается внутри `sip.conf`),
а видеокодек — в настройки приложений. Проверено: при включении видеозвонков
в конфигурации появляется `allow=vp8`.

### Уведомления о пропущенных вызовах (2026-10-10, сделано)

Наблюдатель за вызовами слушает события Asterisk по AMI и сообщает
о неудачных попытках дозвона. Что сделано и что выяснилось на живом
стенде:

- **События берутся из AMI**: DialBegin, DialEnd, Hangup. Своё чтение и
  разбор блока «ключ: значение» — библиотека ради этого не нужна, а
  поведение при обрыве связи нужно своё (соединение восстанавливается
  само: звонки идут круглосуточно).
- **Права AMI пришлось расширить**: пользователю `nvr` в `manager.conf`
  добавлена категория `call`. Без неё состав абонентов виден, а сами
  звонки — нет, и наблюдатель молча стоял бы впустую. Правка сделана и в
  шаблоне, и в `install.sh`; на живом Asterisk нужен `manager reload`.
- **Пропущенным считается каждая неудачная ветвь** (`DialEnd` со статусом
  не ANSWER). Оператор просил сообщать о каждой трубке отдельно: не
  дозвонились до трёх — это три новости. Различаем «не ответили»
  (NOANSWER, CANCEL), «занято» (BUSY) и «недоступен»
  (CONGESTION, CHANUNAVAIL).
- **Журнал звонков** (`sip_calls`, миграция 034) ведётся целиком:
  и неудачные, и состоявшиеся вызовы. Запись делается до уведомления, а
  уникальный индекс по (call_id, to_number) не даёт записать один вызов
  дважды (например, после перезапуска сервера).
- **Каналы выбираются по галочкам того, кто звонил** («панель у калитки —
  в этот чат»), а не по общим правилам событий камер: у вызова нет ни
  камеры, ни класса объекта, и правило отбора к нему неприменимо.
- **Запись вызова**: при звонке запускается сегментная запись с камеры
  устройства, а после неудачи собирается клип вокруг звонка и
  прикладывается к сообщению. Камера берётся из привязки абонента
  (`sip_accounts.camera_id`), отдельного списка камер для домофонии нет.
- Проверено на живых звонках: 101 → 302 («недоступен»), 101 → 301
  («не ответили», ждали 30 с), 101 → 109 и 101 → 115 («разговор
  состоялся»). Записи в журнале, сообщения в Telegram и клип на месте.

**Что осталось от записи**: **звука в записи вызова нет**. Рекордер
(`recorder_service`) намеренно берёт только видеопоток (`-map 0:v:0`) —
комментарий в коде объясняет причину: аудио с камер часто несовместимо
с fMP4, и включение звука сломало бы запись событий камер. Запись вызова
наследует это поведение. Чтобы получить вызов со звуком, нужен отдельный
поток записи (видео + аудио) именно для вызовов — это следующий шаг, и
его надо делать с проверкой на живой панели: формат аудио у домофонов
разный.

Галочка в карточке абонента переименована в «Запись вызова»: обещать
звук, которого нет, нельзя.

## Звонки в мобильном приложении (2026-10-09)

Задача от владельца: каждый, кто входит в систему, должен получить свой
внутренний номер, приложение — зарегистрироваться само, а процесс должен
выживать в фоне (Android иначе его закрывает).

**1. Линия у учётной записи.** Миграция `033_sip_user_lines`: у абонента
появился владелец (`sip_accounts.user_id`, каскадное удаление, одна линия на
человека). Номер берётся автоматически из свободных `3XX` (начиная с `301`:
`300` был занят браузерным тестом WebRTC). Пароль линии — свой, не пароль
учётной записи: он лежит в памяти телефона, а пароль от входа даёт доступ ко
всей установке.

Линия выдаётся в двух точках: при создании пользователя и при запросе своей
линии — так она появляется и у тех, кто заведён раньше, без действий
администратора. Смена имени пользователя меняет подпись линии, но не номер:
номер уже прописан на телефоне. Удаление пользователя убирает линию и
освобождает номер.

**2. Реквизиты приложению.** `GET /api/v1/sip/my-line` отдаёт номер, пароль,
SIP-URI и готовый адрес транспорта `ws://<сервер>:8088/ws` (порт — из
`ASTERISK_WS_PORT`). Правило доступа стоит выше общих правил раздела: линия
нужна любому вошедшему, иначе звонки работали бы только у администратора.

**3. Приложение.** SIP over WebSocket через JsSIP, WebRTC — из
`react-native-webrtc`. В браузере JsSIP узнаёт свой адрес из адресной строки,
в приложении её нет, поэтому `contact_uri` и `via_host` задаются явно: без
них станция подставляет хост `xxxx.invalid`, и регистрация висит без единой
ошибки (проверено на живом Asterisk). Потоки собираются из дорожек
получателей — у `react-native-webrtc` нет `getRemoteStreams`, хотя в
объявлениях JsSIP они есть.

Экран звонков — список абонентов и групп; экран вызова — оверлей поверх
всего приложения (входящий приходит в любой момент), с видео, микрофоном,
громкой связью и набором DTMF для открытия двери.

**4. Фон.** Android останавливает свёрнутое приложение вместе с соединением,
поэтому линию держит служба переднего плана с постоянным уведомлением
(`SipForegroundService`, типы `dataSync|microphone` для Android 14+).
Уведомление показывает состояние линии и имя звонящего.
