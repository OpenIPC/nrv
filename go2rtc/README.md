# go2rtc — медиасервер

Заменил MediaMTX (см. `plans/go2rtc-migration.md`). Принимает потоки камер,
отдаёт их браузеру по WebRTC (или MSE/HLS) и внешним системам по RTSP.

## Роли и порты

| Порт | Что это | Кто ходит |
|---|---|---|
| 1984 | API, WebUI, MSE (WebSocket), HLS | бэкенд, браузер оператора, мобильное приложение (через прокси бэкенда) |
| 8554 | RTSP | ffmpeg самого go2rtc (звук), бэкенд |
| 8555 | WebRTC (TCP+UDP) | браузер оператора |
| 9784 | RTSP для внешних систем | nginx (`rtsp-proxy`) → 8554 |

### Пароль на RTSP

`rtsp.username` / `rtsp.password` в конфиге (значения берутся из
`EXTERNAL_RTSP_USER` / `EXTERNAL_RTSP_PASS`) закрывают RTSP от внешних
потребителей. Важная особенность: **для адресов localhost go2rtc проверку
отключает сам** — поэтому внутренние потребители (ffmpeg звука, бэкенд,
внешние alias-источники на `rtsp://127.0.0.1:8554/...`) пароля не знают,
а запрос из сети — знают. Проверено на живом: 9784 без данных →
`401 Unauthorized`, с `viewer:viewer` → `h264`, с `127.0.0.1` без данных →
`h264`.

Контейнер детектора в bridge-сети — уже не localhost, поэтому ему адрес
передаётся вместе с паролем (`GO2RTC_RTSP` в `docker-compose.yml`).

Отдельного порта для HLS нет: go2rtc отдаёт его по API-порту
(`/api/stream.m3u8?src=`). Проверено на версии 1.9.14: ключ `hls.listen`
в конфиге игнорируется, отдельный порт не открывается.

В **браузере** HLS не используется — там MSE и WebRTC: HLS собирал сегмент
под каждого зрителя и потому стартовал медленно (до 13 секунд). HLS остался
для **нативных клиентов** (мобильное приложение на ExoPlayer, сторонние
плееры), которые MSE не умеют. Бэкенд проксирует его на привычный путь
`/api/v1/cameras/{id}/hls/index.m3u8?token=` — приложение не знает ни о
go2rtc, ни о портах.

Сервис работает в **host-сети**: камеры живут в локальной сети, а WebRTC
должен предлагать браузеру адрес без NAT. Из bridge-контейнеров (детектор,
rtsp-proxy) go2rtc виден как `host.docker.internal`.

## Потоки

Имя потока — это id камеры (тот же, что UUID в базе):

| Имя | Что внутри |
|---|---|
| `<id>` | основной поток камеры |
| `<id>_sub` | субпоток |
| `<id>_audio` | звук камеры, перекодированный в AAC (`ffmpeg:...#audio=aac`) |
| `cameras/<N>/streaming/<main\|sub>` | внешние адреса (канал N-1) |

Потоки регистрирует **бэкенд** через API (`PUT /api/streams?name=X&src=Y`) —
адреса и пароли камер лежат в базе и в конфиг не попадают.

## Особенности API (проверено на живом)

- Параметры — **только в строке запроса**. Если передать их в теле, приходит
  `200 OK` и пустой объект, а поток НЕ создаётся: ошибка выглядит как успех.
- Повторный `PUT` с другим `src` перезаписывает поток — отдельного
  обновления не нужно.
- Удаление — по параметру `src` (не `name`) и идемпотентно: 200 и для
  несуществующего потока.
- Проверка камеры (probe) — `GET /api/streams?src=<имя>&microphone=pcmu`.
- Публикация в неизвестный поток **отклоняется** — поэтому звук не
  публикуется, а перекодируется самим go2rtc источником `ffmpeg:...#audio=aac`.
- Готовность потока узнать нельзя: go2rtc подключается к камере только
  когда её смотрят. Доступность камер проверяет бэкенд TCP-соединением.
- Одновременная регистрация потоков и чтение `GET /api/streams` — гонка
  внутри go2rtc: запрос списка может упасть с паникой в JSON-сериализации
  (`index out of range`). Паника глушится обработчиком HTTP — сервис живёт,
  теряется только один ответ. Поэтому опираться на этот запрос нельзя:
  статус камер бэкенд определяет TCP-проверкой самой камеры.
- Обратная сторона ленивости: если потребитель отключился, go2rtc пишет в
  лог `read ... i/o timeout` и переподключается при следующем зрителе.
  Это норма, а не сбой.

## Двусторонний звук

Работает у камер, которые отдают в SDP `a=sendonly` (ONVIF Profile T).
В этом парке таких 4: `.12`, `.75`, `.87`, `.106` — все на OpenIPC/Majestic.
Подключается вторым источником потока: `rtsp://...#backchannel=1`, и микрофон
браузера уходит в камеру. **В браузере микрофон доступен только по HTTPS**
(ограничение Chrome, не сервера).

## Отладочный скрипт

`add-cameras.sh` добавляет камеры из базы вручную — только для диагностики,
когда бэкенд не запущен. В обычной работе потоки регистрирует бэкенд.
