# Правила работы над проектом

Документ описывает обязательные правила для любых агентов и разработчиков,
работающих с этим репозиторием. Правила появились не сами по себе — каждое
вытекает из конкретной ошибки, которая уже случалась в этом проекте.
Поэтому здесь у каждого пункта указано, **почему** он такой.

---

## 1. Комментарии в коде — по-русски и с объяснением «почему»

**Правило.** Комментарии пишутся на русском языке. Комментарий объясняет
**причину** решения, а не пересказывает код.

```go
// ПЛОХО: пересказ кода — читателю не даёт ничего
// Увеличиваем счётчик на единицу
counter++

// ХОРОШО: объясняет, почему именно так
// Счётчик увеличиваем после успешной записи, а не до неё: иначе при
// ошибке базы счётчик окажется больше числа реально сохранённых записей,
// и при возобновлении синхронизации часть данных потеряется.
counter++
```

**Почему.** Проект рассчитан на размножение по домам и офисам, и читать
его будут разные люди. Пересказ кода они прочитают и без комментария, а
вот причина выбора между двумя рабочими вариантами из кода не видна.

**Что объяснять обязательно:**

- Неочевидные константы и таймауты — откуда взялось значение.
- Обходные пути — что именно сломано у вендора или в протоколе.
- Проверки, которые выглядят избыточными, — от какой ошибки защищают.
- Порядок операций, если он важен.

---

## 2. Не коммитить без явной команды

**Правило.** Коммит создаётся только по прямой просьбе. «Сделай», «исправь»,
«добавь» — это просьба про код, а не про коммит. Отдельно ждать слов
«закоммить», «сделай коммит».

**Почему.** Пользователь собирает изменения по своему усмотрению и иногда
хочет сначала проверить работу в живом интерфейсе. Коммит, созданный
заранее, ломает этот порядок и попадает в историю раньше проверки.

---

## 3. После коммита — пуш в оба удалённых репозитория

**Правило.** Каждый коммит отправляется **в оба** remote:

```bash
git push origin <branch>     # GitHub
git push gitverse <branch>   # GitVerse
```

**Почему.** Проект публикуется на двух площадках одновременно. Если
отправить только в один, вторая площадка отстанет, и версии разойдутся —
пользователь получит разные состояния проекта по двум адресам.

---

## 4. Перед началом работы — прочитать план

**Правило.** Перед изменениями в функциональности прочитать:

- `plans/openipc-deep-integration.md` — план по камерам OpenIPC;
- `plans/video-surveillance-server-plan.md` — общий план сервера;
- профильный документ в `docs/` по теме задачи.

**Почему.** В планах записаны факты, проверенные на живом оборудовании, и
уже принятые решения. Без них легко предложить то, что уже пробовали и
отвергли, или сломать сделанное. В разделе «Что уже проверено на камерах
парка» лежат измерения, которые ниоткуда больше не получить.

**Признак того, что план надо обновить:** если в ходе работы выяснился
факт, противоречащий плану, — план правится, а не остаётся с ошибкой.

---

## 5. Универсальность вместо привязки к установке

**Правило.** Система проектируется так, чтобы её можно было повторить в
другом доме или офисе без правки кода.

**Как проверять.** Система не должна требовать знания о железе, которое
может получить сама. Если для работы нужно заранее внести устройство в
список в коде — это признак привязки к текущей установке.

**Почему.** В другой установке будут другие модели камер, другие адреса
и другие частоты сети. Всё, что вписано в код как константа, там
окажется неверным.

**Что можно опираться на конкретику:** адреса и учётные данные вводятся
через интерфейс и хранятся в базе, а не в коде.

---

## 6. Факты с оборудования — а не из документации

**Правило.** Утверждения о работе устройств берутся с живых устройств:
команды по SSH, запросы к API, замеры. Расхождение с документацией
отмечается в плане отдельно.

**Почему.** Документация уже дважды расходилась с реальностью: у
контроллера Z5R WEB BT настоящие эндпоинты отличаются от описанных в PDF
(реальные найдены в веб-интерфейсе устройства), а на камерах парка
набор настроек зависит от SoC, а не от модели.

**Важно при проверке запросов.** Успешный код ответа ещё не означает
успех операции. Уже случалось: запрос с неверным параметром пагинации
возвращал `200` и **пустой список** — все камеры оказались офлайн без
единой ошибки в логах. Проверять надо **содержание** ответа, а не только
код.

## 7. Структура репозитория

| Каталог | Назначение |
|---|---|
| `backend/` | Go 1.22, chi, pgx, zerolog. Версия Go в `go.mod` не поднимается |
| `backend/internal/service/acs/` | адаптеры СКУД: по одному файлу на вендор |
| `backend/migrations/` | SQL-миграции, парные `.up.sql` и `.down.sql` |
| `webui/` | React 18 + TypeScript + Vite |
| `plans/` | планы и результаты проверок |
| `docs/` | документация по подсистемам |
| `firmware/` | прошивки собственных устройств |

**Порты.** Backend API — `8080`, Web UI — `3001`, MediaMTX API — `9997`.

---

## 8. Проверка перед завершением работы

- [ ] Сборка проходит: `cd backend && go build ./...`
- [ ] Затронутые тесты проходят
- [ ] Комментарии объясняют «почему», а не «что»
- [ ] План в `plans/` обновлён, если выяснились новые факты
- [ ] Изменения проверены на живом оборудовании, если это возможно
