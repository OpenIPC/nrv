# Переводы интерфейса

Документ для тех, кто хочет поправить или добавить перевод веб-интерфейса.

Отдельно оговорён корейский: **сейчас перевод сделан южной нормой, хотя на
переключателе стоит флаг КНДР.** Почему так и как это исправить — в разделе
[«Корейский язык»](#корейский-язык).

---

## README на других языках

Кроме интерфейса переведён и главный документ проекта:

| Файл | Язык |
|---|---|
| [README.md](../README.md) | Русский — **основной, источник** |
| [README.en.md](../README.en.md) | Английский |
| [README.zh-CN.md](../README.zh-CN.md) | Китайский (упрощённый) |
| [README.ko.md](../README.ko.md) | Корейский (южной нормой) |

В начале каждого файла стоят ссылки на остальные — чтобы человек, случайно
попавший не в тот файл, сразу нашёл свой язык.

### Правило: правка основного README — правка всех четырёх

Русский файл — источник. При изменении любого раздела его нужно повторить в
трёх остальных, иначе переводы начнут расходиться с оригиналом, и человек,
читающий английскую версию, будет получать неверные сведения о том, как
устроена система. Это хуже отсутствия перевода: отсутствие видно, а
устаревший текст выглядит достоверным.

**Что это значит на практике.** Каждый новый раздел, новая запись в «Что
нового» и новое ограничение обходятся в четыре правки вместо одной. Если
это становится обременительным, есть два выхода:

1. добавить раздел только в русский README и **явно написать в нём**, что
   раздел пока не переведён;
2. вынести историю изменений из README в отдельный `CHANGELOG.md` и переводить
   только документацию, а историю оставить на одном языке — так делают многие
   проекты, потому что старые записи читают редко, а места они занимают много.

Переводить стоит не дословно, а по смыслу: подписи на скриншотах, названия
пунктов меню и сообщения сервера в переводах остаются русскими, потому что
снимки сделаны на русской версии интерфейса. Это нормально и не требует
переделки картинок.

## Как это работает

Переводы лежат в коде, а не тянутся из сети:

```
webui/src/i18n/
├── index.ts              — настройка библиотеки, список языков
└── locales/
    ├── ru.ts             — русский, язык-источник
    ├── en.ts
    ├── zh-CN.ts
    └── ko.ts
```

Библиотека — [i18next](https://www.i18next.com/) вместе с `react-i18next`.

**Русский язык — запасной.** Если строки нет в словаре выбранного языка,
показывается русская. Это сделано намеренно: переносить полторы тысячи
подписей за один раз нельзя, любая пропущенная строка показала бы
пользователю ключ вида `nav.cameras` вместо слова. С запасным языком
непереведённое просто остаётся русским, и переводить можно постранично.

Отсюда практическое следствие: **неполный перевод — это нормально и не
ломает интерфейс.** Если вы перевели три экрана из пятидесяти, ничего не
сломается, три экрана будут на вашем языке.

## Как проверить экран

Непереведённую подпись глазами не поймать: забытая строка теряется среди
переведённых, а на редкий экран можно вообще не зайти. Поэтому для
проверки есть скрипт — он открывает экран под выбранным языком, обходит
все текстовые узлы и атрибуты (`title`, `placeholder`, `aria-label`) и
печатает всё, где осталась кириллица.

```bash
node scripts/check-i18n-page.js /plans zh-CN
NVR_TAB='固件' node scripts/check-i18n-page.js /cameras/<id> ko
```

Кириллица в именах устройств — это данные из базы, они и должны
остаться русскими: скрипт их показывает, но отличает по контексту.

`NVR_TAB` нажимает кнопку перед проверкой — для подписей, которые лежат
на закрытой по умолчанию вкладке. Несколько кнопок разделяются
вертикальной чертой и нажимаются по порядку: есть подписи, которые
появляются только после двух действий (открыть окно камеры, затем нажать
«Проверить»).

**`NVR_EXPECT` обязателен, когда экран открывается нажатием.**

```bash
NVR_EXPECT='摄像机设置' NVR_TAB='固件' node scripts/check-i18n-page.js /cameras/<id> zh-CN
```

Без него результат «русских подписей не найдено» ничего не доказывает:
вкладка могла не открыться, и скрипт осмотрел бы прежний экран. Так уже
случилось — проверка настроек камеры один раз отчиталась об успехе, не
открыв вкладку. Если строка не появилась за 15 секунд, скрипт сообщает об
этом и завершается с кодом 2.

## Как поправить перевод

1. Откройте нужный файл в `webui/src/i18n/locales/`.
2. Найдите ключ. Ключи сгруппированы по разделам: `nav` — меню, `common` —
   общие слова, `serverPage` — страница настроек сервера и так далее.
3. Замените текст справа от двоеточия. **Ключ менять нельзя** — по нему
   строка ищется в коде.
4. Соберите интерфейс и проверьте:

```bash
cd webui
npx tsc --noEmit          # опечатка в синтаксисе видна сразу
docker compose build webui && docker compose up -d webui
```

5. Откройте `http://<адрес сервера>:3001/server` и переключите язык —
   переключатель стоит на этой странице.

### Что важно при переводе

**Подстановки.** В строках встречаются вставки вида `{{count}}` или
`{{name}}`. Их надо переносить в перевод **без изменений** — это места, куда
подставится число или имя. `{{count}}` можно двигать внутри фразы: в
китайском и корейском порядок слов другой, и это нормально.

**Названия на самих языках.** Пункты меню языков даны как `Русский`,
`English`, `简体中文`, `한국어` — на самих языках, а не по-русски. Причина
простая: человек, которому нужен китайский, слово «Китайский» может не
прочитать, а «简体中文» прочитает сразу.

**Длина строк.** Кнопки и пункты меню рассчитаны на русскую длину. Немецкий
или английский текст часто длиннее — если подпись не влезает, лучше
сократить, чем ломать вёрстку.

**Не переводите по словарю.** Перевод, сделанный машинно и без проверки,
хуже русского текста: читатель не понимает, что перед ним, и не догадывается,
что можно переключить язык обратно. Лучше перевести один экран хорошо, чем
пятьдесят плохо.

### Как понять, какие экраны ещё не переведены

Пока в файле стоит русский текст, экран на других языках показывает русский.
Найти остатки можно так — команда ищет русские буквы в разметке страниц:

```bash
cd webui && grep -rlP "[\x{0410}-\x{044F}]{3,}" src/pages src/components
```

Файлы с русскими строками внутри `t('...')` — это подсказки, уже
переведённые в словаре; важен русский текст **вне** вызовов `t()`.

## Как добавить новый язык

1. Создайте `webui/src/i18n/locales/<код>.ts` по образцу `en.ts`.
2. Зарегистрируйте язык в `webui/src/i18n/index.ts` — в списке `LANGUAGES`,
   в объекте `resources` и в импортах.
3. Добавьте флаг в `webui/src/components/Flags.tsx`: функция вида
   `FlagXX` и ветка в переключателе `Flag`. Флаги нарисованы вектором прямо
   в коде, внешних картинок нет — это сделано потому, что сервер может
   стоять в сети без выхода наружу, и любая загрузка извне станет пустым
   местом вместо флага.

Флаги — государственные символы и в большинстве стран не охраняются
авторским правом, поэтому их воспроизведение в коде ничем не ограничено.

## Корейский язык

**Что сделано сейчас:** перевод на корейский выполнен **южной нормой**
(Республика Корея), а на переключателе стоит **флаг КНДР**.

Это сделано осознанно и по просьбе заказчика из КНДР: флаг должен быть своей
страны. Но северокорейская норма — это не «тот же корейский с другим
флагом», а **отдельный язык перевода**:

- свой код языка — `ko-KP`, а не `ko`;
- другая лексика и другие обращения к пользователю;
- другие написания и другая терминология (в том числе компьютерная);
- слов, привычных южнокорейскому читателю, в северном тексте просто нет.

Одной заменой слов в словаре это не делается: нужен **носитель северной
нормы**, который перечитает текст целиком.

Поэтому мы поставили задачу так:

1. Сейчас — флаг КНДР и южнокорейский текст. Интерфейс понятен, но написан
   не той нормой, которая нужна читателю.
2. Когда найдётся переводчик с северной нормой — текст переводится заново и
   получает код `ko-KP`. Флаг при этом не меняется.

Если вы читаете северокорейскую норму и хотите помочь — правьте
`webui/src/i18n/locales/ko.ts` и присылайте изменения. **В первую очередь
нужен перечитчик, а не переводчик с нуля**: русский текст-источник уже есть,
нужно переложить его на северную норму.

## Чего в переводе нет

- **Серверных сообщений.** Тексты ошибок приходят с бэкенда готовыми
  строками по-русски: описание сбоя от устройства, ответ мессенджера,
  исходный текст `ffprobe`. Это данные, а не подпись интерфейса — перевести
  их можно только на стороне сервера, а он не знает языка оператора. Перевод
  интерфейса их не затрагивает; подписи, которые сервер ставит сам (ход
  обновления прошивки, причина отказа в журнале, замечания к состоянию
  камеры, результат проверки потока), уже заменены на коды — см. раздел ниже.
- **Описаний сбоя от устройств.** Слой работы с камерами
  (`backend/internal/service/majestic_client.go`,
  `cameraapi/hikvision.go`, `cameraapi/beward.go`) составляет сообщения
  сам: «камера недоступна: …», «камера вернула 400», «неверный логин или
  пароль камеры». Их около двадцати, и они едут в интерфейс одной строкой —
  технической подробностью рядом с кодом причины. Это следующий шаг, а не
  забытое место: переводить их надо кодами так же, как уже сделано для
  состояния камеры, но это отдельная работа — сообщения сравниваются через
  `errors.Is` и оборачиваются `%w`, и слепая замена текста ломает ветвления.
- **Названий, приходящих из данных.** Названия камер, планов помещений,
  владельцев карт задаёт пользователь, и они показываются как введены,
  на каком бы языке ни был интерфейс.
- **Форм множественного числа.** В русском их три, в китайском нет вовсе.
  Пока используется одно написание; для языков с несколькими формами это
  отдельная задача.

## Правило для серверного кода: в ответе — код, а не текст

Если сервер отдаёт не данные, а **подпись** — причину отказа, название
группы, статус, — отдавать надо код, а подпись ставить в интерфейсе.

**Почему.** Уже дважды случалось одно и то же: сервер подставлял в ответ
русскую фразу, интерфейс показывал её как есть, и на китайском она
оставалась русской. При этом перевести её на стороне интерфейса было уже
нечем: строка приходила готовым текстом в поле, которое интерфейс
считает данными.

Что именно пришлось переделывать:

- сводка по логам — сервер группировал строки под ключами
  `неизвестный источник` и `без программы`
  (`backend/internal/repository/postgres/camera_log_repo.go`);
- журнал отправок уведомлений — причина отказа писалась в базу готовой
  фразой (`backend/internal/notify/rule.go`);
- подсказка о разобранной ссылке прокси возвращалась готовым текстом
  (`webui/src/utils/proxyLink.ts`);
- результат проверки RTSP-потока приходил одной фразой
  (`backend/internal/service/camera_service.go`): теперь сервер отдаёт код,
  а технические поля (кодек, разрешение, звук) — отдельно, чтобы подпись
  собиралась в интерфейсе. Сырой текст `ffprobe` остаётся как есть: это
  подробность конкретной сборки, и её разбирать нельзя.

**Как надо.** Сервер возвращает код (`low_confidence`, `quiet_hours`),
интерфейс переводит его по таблице. Если код незнакомый — показывать
значение как есть: в старых записях лежит прежний русский текст, и
терять его нельзя, по нему разбирают случаи, случившиеся раньше.

**Один код — одно место разбора.** Если результат показывается на
нескольких экранах, разбор кода выносится в общий файл
(`webui/src/utils/streamProbe.ts` для проверки потока): иначе подписи
разъедутся, и одна и та же ошибка будет называться по-разному в сканере
сети и в карточке камеры.

**Осторожно с уже накопленными данными.** Перевод на коды означает, что
в базе лежат значения двух видов. Миграция
`027_notification_reason_codes` переводит старые записи на коды — при
добавлении новых кодов нужна такая же миграция, иначе один журнал будет
показывать и «тихие часы», и `quiet_hours`.

**Что кодом быть не должно.** Текст, который пришёл от устройства или
стороннего сервиса (сообщение об ошибке от Telegram, имя камеры), — это
данные. Их показываем как пришли.
